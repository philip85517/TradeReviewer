# 03 — 并发修改展示信息时可能丢失一次修改

State: open
Status: deferred-by-user
Assignee: coordinator

## 问题与例子

同一条展示信息同时被两个人修改时，一个人改名称，另一个人改翻译名称。预期是两项修改都保留，或者后提交者收到冲突提示；当前实验原型两次提交都显示成功，但最终只保留其中一项。由独立审查用两个写入线程实证，详见 [审查报告](../reviews/combined-01/REVIEW.md)。

原因是原型只检查成交记录的版本，而修改名称不会改变成交版本；两次修改因而都被当作有效。SQLite 即使把写入排队，也不会自动识别第二次携带了过期内容。

## 处理范围

本轮仅在稳定的隔离数据和单写入者条件下测量读取与更新成本，该问题不阻断这个实验；不能据此声称真实产品的并发修改安全。需要真实产品落地时，再设计展示信息的独立版本检查、细粒度更新或等价的冲突处理，并单独测试。当前不改产品代码，也不把问题当成已修复。

## 优先级调整（2026-10-29）

用户说明当前为单机使用，暂缓人工并发修改问题，优先聚焦性能优化。保留上述失败证据和问题，不在本轮修复；性能实验须明确采用单写入者条件，不能将此项标为通过。单机下的自动后台任务等是否会形成并发尚未验证，正式产品落地前仍需重新评估。此调整不改变其他已暂停任务的状态，也不降低数据正确性与首页、交易库完整首屏各 1 秒的目标。
