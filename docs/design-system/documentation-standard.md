# 图文视觉设计文档标准

标准 ID：VDF。版本：1.0，2026-10-11。适用于 TradeReview 各页面、公共组件及视觉交互的设计文档。用户要求将当前图册的形式沉淀为项目规范；本标准规范**如何记录与维护设计**，具体产品外观仍以对应功能已确认的契约为准。

新建文档从[可复制模板](templates/visual-design.template.md)开始。[已确认锁定的复盘工作区图册](baselines/2026-10-11-clean-review-r1-locked/RELEASE.md)是完整形式示范；当前批准边界以其RELEASE为准，候选参数仍需真实组件校准，图版不等于运行金图。文档编写检查不能替代真实产品验收。

## 1. 使用入口与工作量

| 工作范围 | 最低图文交付 | 可复用内容 |
| --- | --- | --- |
| 整页新增、整页视觉重构、建立整页基线 | 一张纯净整页图；范围内文字、颜色、控件、侧栏、图表/列表、适用交互与响应式专题；逐项规则与验收映射 | 已确认公共规范直接引用，不另造一套字号/颜色 |
| 局部控件、状态或密度调整 | 一张说明所在上下文的整页图或有效引用；受影响局部图；适用的前/中/后或普通/选中/编辑等状态；规则、影响面及验收 | 引用有效的整页基线，只更新受影响章节和图像 |
| 只做现状诊断 | 最新运行证据、问题位置、实测参数、任务影响、原因判断、拟议规则及验收方法 | 明确区分实测与推断；不因检查自动修复 |
| 只整理文档格式或索引 | 结构、链接、来源/状态一致性、差异检查与文档审查 | 无需启动无关控件操作或数据库验收 |

不要求所有任务都生成12张图，也不要求重新审批已确认且未变化的设计。没有原稿时引用已记录需求及现有视觉约定，补齐必要画面；不得凭“没有设计图”放弃设计说明。历史文档不批量重写，下次作为新任务依据时先核实状态和证据有效性。

## 2. 文件组织与权威来源（VDF01）

长期基线保存在 `docs/design-system/baselines/<YYYY-MM-DD-slug>/`，真实实现归档保存在 `docs/design-system/versions/<YYYY-MM-DD>/`。目录名不代表已经批准或验收，入口必须写明状态。可保留已有命名；局部任务可在既有版本追加受影响专题，不机械增加文件。

| 内容 | 默认位置 | 职责 |
| --- | --- | --- |
| 导航、范围、状态、版本与文件角色 | `README.md` | 告诉读者从哪张图开始、哪些已确认、哪些待确认 |
| 图片＋说明＋规则 | `visual-design.md` 或既有 `illustrated-guide.md` | 核心评审内容，可将局部文档合并为一份 |
| 图片、局部图、动效证据 | `images/` | 与文档一起保存，不能只指向临时目录或易失本机URL |
| 图片元数据与指纹 | 文档图片登记表；图片多时用 `image-manifest.json` | 表格和JSON只选一处作为指纹权威，另一处引用 |
| 实现映射与实际验收 | 原功能计划、`DESIGN-COVERAGE.md`、验收文件 | 沿用[拆票标准](../agents/task-decomposition.md)和[UI验收模板](../agents/ui-task-templates.md)，不另建相冲突的流程 |
| 网页图册（可选） | `visual-spec.html` | 可浏览的派生展示；规则内容以Markdown权威文件为准 |

默认核心文档可同时容纳规则；若已有 `visual-baseline.md`，它作为产品规则权威，图文册的参数表是带规则ID的解释视图。HTML与图文册有差异时先修正展示并登记，不能同时维护两个不同的设计结论。生成HTML应记录源文件与再生成方式；手工同步必须核对章节、图片、规则和状态一致。

`.scratch` 继续用于本地任务、调试和过程证据。长期引用的必要图片、最终规则和接受结论应进入上述稳定目录；历史临时链接注明追溯用途，不冒称其他机器一定可读。内部文档采用相对路径，交付聊天使用绝对文件链接。外部参考保存原始来源及访问日期，尊重其使用权限。

## 3. 首页与章节结构（VDF02–04）

首页先说明用户任务和设计重心，紧接一张整页图与其状态说明，随后给出目录和文档角色。不要让用户先阅读一大段术语才能看到界面。

每个专题采用固定顺序：

1. **图片**：一张完整画面或明确编号的局部/连续步骤；显示适用状态，能查看原尺寸。
2. **描述**：用普通中文说明用户在做什么、应该先看到什么、为什么采用此比例/位置、付出了什么取舍。局部图说明它位于整页哪里。
3. **规范**：用规则表给出作用域、角色/尺寸/行为、数值分类、例外及验收方法；引用稳定规则ID。
4. **待确认与未验证**：只列该专题尚缺的决策或证据，并明确下一步负责人。

专题应按任务阅读顺序组织：整页 → 基础文字/颜色/空间 → 工作区与公共控件 → 操作状态 → 适用的阶段/响应式/长内容 → 保存/输出 → 例外及验收。可以合并或省略不适用专题，但须注明范围依据。图片中的说明箭头、中心线、编号与图外标题是文档辅助层，不进入纯净产品画面。

## 4. 图片身份与可比条件（VDF05–06）

每张图有稳定图ID，例如 `IMG-01`；规则使用原项目ID，例如 `CB15`、`E09`，新增规则用该功能唯一前缀。图片变更保留ID并增加版本，不复用ID表达另一种场景。同一图片允许覆盖多条规则；每条范围内规则必须能找到对应画面或明确的非视觉依据。

| 必填元数据 | 记录要求 |
| --- | --- |
| 来源类型 | 设计示意、运行实拍、历史参考、运行金图；动效另标示意/真实录制。运行金图须有相应版本的独立接受依据 |
| 文件与身份 | 图ID、文件路径、章节/规则ID、生成或采集时间、作者/来源；最终资源记录SHA-256与实际像素尺寸 |
| 源版本 | 原稿版本或源码commit；未提交修改有内容指纹。可编辑源、导出方式和限制单列，不只记录生成图片的时间 |
| 环境 | CSS视口、DPR、浏览器缩放、主题、字体栈与实际字体证据、浏览器/系统；未知明确写未知，不从PNG尺寸反推 |
| 场景 | 数据fixture版本、正文、阶段、导航/面板开合、选中/焦点/编辑、滚动位置；图表还记录时间/价格范围和双截止 |
| 处理 | 是否裁切、缩放、拼接或添加说明；局部图保留整页来源及裁切区域；多场景图版逐格注明状态 |
| 状态 | 设计批准状态和依据；运行验证状态和证据。两者分别记录 |

公共环境可在登记表上方只写一次，各图记录不同项。图版高度不是产品CSS视口；PNG像素尺寸也不是CSS尺寸。未知测量不得编造。字体栈或字体加载成功不证明实际中文字形来源。

待评审画面推荐称“待确认设计图”，避免“设计确认图”被误读为已批准。批准状态必须有文字与决定依据，不能只靠图片名称或颜色表达。

候选方案只在确有值得选择的布局/密度差异时增加。对照候选固定数据、完整文案、阶段、CSS视口、DPR/缩放和图表范围；把授权变化单列。运行与设计采用同一目标态对照；点击前/中/后的不同状态是时序证据，不能称作同态视觉比较。

## 5. 规则写法与数值来源（VDF07–08）

| 分类 | 含义 | 后续使用 |
| --- | --- | --- |
| 已确认规则 | 用户决定或有效设计契约，有准确来源 | 在适用范围内约束实现，变更必须记录决定依据 |
| 候选参数 | 尚未确认的构图、密度或尺寸 | 在完整真实组件中校准，再登记获选版本；画出来不等于批准 |
| 当前实测 | 本次运行的rect、computed style或其他实际观察 | 描述现状，可是问题，不自动成为目标 |
| 样本数据 | 保持图中业务状态自洽的价格/数量/正文 | 用于复现，不写死为产品默认值 |

规则表至少有“ID/对象与状态、具体约束与单位、分类与依据、例外、验收动作/证据”。写明字号/字重/行高、图标可见尺寸与命中尺寸、间距方向、颜色语义及状态；比例需说明相对哪个容器。不允许只写“高级感”“优化层级”“紧凑一些”。颜色引用现有token与配置，不因图中的样本色替换用户盈亏设置。

诊断每个主要问题时，记录：位置/相关组件或样式 → 新鲜截图及区域 → 实测现象 → 对任务的影响 → 原因判断及确定程度 → 修改规则 → 验收。来源只能支持其真实范围：读取CSS可证明声明值，截图可证明画面，实际操作才证明行为。

## 6. 交互与状态的图文表达（VDF09–10）

根据本次控件评估普通、悬停、键盘焦点、选中、拖动、编辑、禁用/只读、展开/收起、加载、空、失败、取消、长内容等状态是否适用；无需为没有异步行为的按钮虚构加载态。

交互专题至少写“前态 → 用户动作/输入方式 → 过程反馈 → 完成结果 → 取消/失败与恢复”。拖动、绘图等连续动作给出首点、中间预览、释放后的画面或录像；记录光标、命中区域、选中反馈和几何是否变化。静态图片不能证明动画时长、拖动灵敏度、系统光标或持久化通过，动效示意也不能充当真实录制。

复盘工作区专用契约仍按该功能规格记录：S0/S1/S2、行情/成交独立截止、未来信息各入口、原文与补充的形成阶段、计划与实际、视野以及保存/重开。文档版式不得隐藏关键价格、删短固定判断，或因某参考图没有画出而省略领域规则。

## 7. 文档展示版式（VDF11）

图册应让图片优先、文字可读、参数易于查找。当前[网页图册](baselines/2026-10-11-clean-review/visual-spec.html)可作默认展示样式，下表仅用于**设计文档页面**，不是产品控件token：

| 部位 | 默认展示方式 |
| --- | --- |
| 导航 | 桌面章节导航约248px；较窄空间约210px；窄窗转文档顶部目录，不压缩产品图 |
| 正文与标题 | 正文16px / 1.8；主标题32px / 1.3；专题标题24px / 1.5；表格14px；图注12px。中文系统回退明确 |
| 图片 | 保持原始比例，容器宽度内缩放，点击查看原图；裁切图注明范围，不拉伸或靠裁切隐藏问题 |
| 图文间距 | 章节分隔清楚；图、描述、规则连续出现；说明与产品画面分离 |
| 表格 | 保留完整单位和规则ID；窄窗在表格容器内滚动，不让整页横向溢出，也不截断数值 |
| 操作与动效 | 链接/重播可用键盘聚焦且有可见焦点；动效遵从减少动态效果偏好；静态步骤可独立理解 |
| 网页状态 | 明确设计/运行来源与批准状态；不得在页头一处写“未确认”，正文却写“已上线通过” |

Markdown也必须可独立阅读，所有图有解释性alt，所有本地资源有效。HTML为可选展示，不要求为小改动建设新网站；选择其他文档载体时保留相同内容结构和状态口径。

## 8. 与设计、开发、验收的衔接（VDF12）

| 环节 | 文档动作 | 接入文件 |
| --- | --- | --- |
| 提出/诊断 | 读现有设计与运行证据，限定范围，补图文和候选参数 | 本文、对应功能规格/来源记录 |
| 评审/决定 | 记录用户对实际画面的选择、适用状态与获选参数；只确认发生变化的内容 | 基线README和决策记录，不由代理自行把草案标已确认 |
| 派发 | 将规则/元素→准确图片及状态→owner/旅程→验收证据逐项映射 | [任务拆解标准](../agents/task-decomposition.md)的 `DESIGN-COVERAGE.md` |
| 实现/复核 | 复用现有主题和公共组件；分开比较功能、状态链和同态视觉 | [开发流程](../agents/development-workflow.md)、[控件审计](../agents/frontend-control-audit.md) |
| 接受/归档 | 实际证据绑定最终版本，记录独立审查与未决项，再收录有效运行金图 | [UI验收模板](../agents/ui-task-templates.md)、版本目录与设计索引 |

兼容实现方案写明每条规则对应的主题token、公共组件、页面/状态入口及当前差距；不默认更换框架或组件库。模板中的实现映射只指向证据/职责，不把猜测的文件位置冻结为产品需求。局部票或文档PASS不代表整页产品通过。

## 9. 版本维护与状态（VDF13–14）

设计状态使用“草案 / 待确认 / 已确认 / 已取代”，按章节或规则记录，允许同册混合状态。记录确认人、时间、用户决定来源及适用范围；文档格式确认、视觉选择、实施授权和产品验收是不同事项，不能互相推定。

证据结论沿用项目 `PASS / FAIL / NOT VERIFIED / NOT APPLICABLE`。未测或不足为NOT VERIFIED；确实不适用时说明范围理由。回归保留先前FAIL/PASS，追加失效原因和复验，不覆盖历史以制造连续通过。设计已确认也可以仍未实现/未验收。

每次变化执行：

1. 读取现有效版本与最新用户决定，列影响规则、图片、状态和依赖。
2. 局部迭代更新受影响章节；改动已确认契约时登记新决定，原版本链接保留。一个版本中已用于接受的资源不无痕覆盖。
3. 同步图片登记/指纹、规则映射与可选HTML；说明变化和未改变范围。
4. 检查链接、原尺寸、图文相符、状态一致；按影响更新设计索引和任务/验收记录。
5. 开发后按现有流程取得新的真实证据；旧证据只在版本与影响面仍有效时复用。

无需每次增加版本目录；同一待确认草案可带时间和指纹修订。一旦成为已确认基线或验收归档，应保留可恢复的版本和变更记录。

## 10. 文档完成检查（VDF15）

- [ ] 入口明确目标、范围、版本、各部分状态、规则权威与当前未决项。
- [ ] 每个范围内主要对象都有“图片＋普通中文描述＋具体规则”，局部图能定位整页。
- [ ] 图片来源、比较环境、fixture与图表状态有记录；未知不编造，最终文件有尺寸和指纹。
- [ ] 规则/元素ID可映射到图片、组件职责、用户旅程与验收；候选/实测/样本不混入已确认规则。
- [ ] 适用状态、连续操作、长内容与响应式有图文；排除项有范围依据，不能记作通过。
- [ ] 本地引用有效，图片可原尺寸查看；HTML存在时与Markdown一致且能阅读。
- [ ] 设计示意、真实证据、用户批准和产品验收分别登记；没有擅自把文档完成写成产品完成。
- [ ] 差异、更新方式和维护责任清楚；重要最终结论可在稳定项目目录找到。

图文素材新建/修改时由非作者直接检查图文相符；只改格式/索引时审查结构和引用即可复用仍有效的图版证据。本清单检查设计文档，产品放行仍须独立通过项目现有适用门槛。
