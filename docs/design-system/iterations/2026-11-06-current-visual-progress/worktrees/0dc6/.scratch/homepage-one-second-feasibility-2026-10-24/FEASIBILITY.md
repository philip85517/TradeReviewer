# 页面打开 ≤1 秒：各环节优化可行性

日期：2026-10-24。性质：只读研究，未实施优化。研究基线：HEAD `58bf0d9` 加现有 dirty 工作树；[887 个基线文件核验](SOURCE-VERIFICATION.json)无新增差异。主代理负责结论与独立复核，三名 GPT-6 Astra Ultra 分别研究服务端、来源模型、启动边界。

**结论：当前“打开页面时枚举全库 → 拉全证券历史行情 → 浏览器构建并校验完整财务来源”的路径，没有支持整体 ≤1 秒的证据。最有希望的方向是将可复用计算移到数据更新路径，打开时读取与当前数据版本一致的紧凑首屏投影，同时拆开首页启动依赖。** 窄查询、批量接口、摘要优化和预构建都值得做，但单独实施均不足以判定达标。所有优化后的耗时仍为 NOT VERIFIED。

## 1. 目标与证据边界

分析口径：服务已启动，从导航开始，到真实首屏指标、持仓、设计要求的首屏曲线完成显示且可交互，合计 ≤1000ms。骨架、空值、旧数据、超时提示、只完成 HTTP 或 React effect 不算成功。此口径是对用户目标的分析假设，不是新批准的设计合同；不能以缩减可见内容来通过。

分别考察：浏览器缓存冷/热、服务重启后持久投影命中、投影未命中、导入/修订后首次访问、外部行情/FX缺失。导航前的进程启动单列；若用户要求把进程启动也计入，当前没有可以承诺 ≤1 秒的证据。开发按需编译单独归因，但凡发生在导航之后，仍计入该次导航总耗时，不得从结果中扣除。统计分位用于发现波动，不能把“整体1秒以内”替换成“仅热访问p95”。

基线来自上一轮已经独立核对的[完整桌面漏斗](../homepage-timeout-funnel-2026-10-24/DIAGNOSIS.md)：1440×900、隔离 SQLite 副本、开发服务器、一次完整插桩样本。不是未插桩生产测速，也不是多次运行的中位数。本轮没有启动/重启服务、操作浏览器、请求业务 API 或访问数据库。当前浏览器的 `/trades` 没有本轮性能样本，以下首页数值不能直接套用到交易库。

已执行快速基线检查两次，均 exit 1 / FAIL：

```sh
python3 .scratch/homepage-one-second-feasibility-2026-10-24/check-opening-slo.py .scratch/homepage-timeout-funnel-2026-10-24/complete-trace.json
```

[输出](BASELINE-SLO.json)：loadEnd=10719.1ms，globalRead开始=14318.2ms，财务超时终态effect=31950.5ms，financialAccepted=false。这是保存事件的门槛检查，**没有重新驱动产品代码，不能作为优化后可变红绿的真实反馈回路**。诊断技能的实时复现证据复用上一轮；本轮以可行性研究为边界，未进入修复与修复后回归阶段。保留整条旅程，避免缩成单函数后丢掉导航成本。后续实施必须建立真实导航→成功财务paint/交互的可运行门槛。

## 3. 为什么现有缓存还不能解决

- SQLite已有行情持久缓存；这次慢的是读取/映射/传输/浏览器加工已有行情，不能把“加缓存”当成尚不存在的能力。连接复用、FX当日缓存及进程内in-flight也已存在。
- `/api/storage/market-data` 当前每个请求调用全量 `getInstruments()`，再全量 `getIntervalCoverage()` 后过滤；`dailyOnly`仍返回此intervalCoverage。见[route:29](../../app/api/storage/market-data/route.ts:29)、[route:39](../../app/api/storage/market-data/route.ts:39)。这是可独立验证的重复工作，不等于整个SQLite引擎慢。
- 来源snapshot每次生成`receiptId`和`knownAt`，再对完整payload编码/SHA；合同明确receipt是读取身份，**不是持久数据库revision**。见[snapshot:15](../../app/lib/storage/homepage-source-snapshot.ts:15)、[contract:13](../../app/lib/storage/homepage-source-contract.ts:13)。原子存储集合不等于成交、行情、FX、别名、客户端观测时间跨接口均已形成同一原子版本。
- 64MiB投影memo属于单个prepared handle；`prepareHomepageV25Source`先clone并hash完整输入，再新建memo。刷新后重新prepare，首读成本已经发生。见[performance:647](../../app/lib/reviews/homepage-v25-performance.ts:647)。
- 选择器虽筛选entries，仍把完整candles/metadata/FX传给prepare，所以“范围内没有entry”也不意味着来源图很小。见[source-model:159](../../app/components/homepage-v25/financial-source-model.ts:159)。
- 首页与交易库共同挂载大工作区；首页reload先等存储与别名就绪，再读原子来源、全证券daily、构造交易库entries、完成acquisition和fromGlobal。见[home入口](../../app/home/page.tsx:1)、[workspace:2233](../../app/components/trade-review-workspace.tsx:2233)。应当分离页面读取职责；不能只给组件外包一个lazy仍保留全部初始化。

`CONTEXT.md`、ADR-0001/0002/0006支持本地Node/SQLite、行情缓存及可复用同步模块的现状。它们不是批准的新首页聚合架构；ADR中旧端口/运行时/路径不覆盖当前`conf`和开发流程。ADR-0006要求区分刷新结果与保留旧数据，优化不能把失败缓存标成新鲜成功。

## 4. 三种路径的取舍

| 路径 | 改动与可保留能力 | 可行性/限制 |
| --- | --- | --- |
| A. 保守修整 | 窄查询、批量读、去重bootstrap和后台读取、来源prepare复用、预构建与页面拆分 | 可先降低成本，改动相对小；浏览器仍接收和加工大来源，无法据此支持严格1秒 |
| B. 请求时生成首页投影 | 服务端一次读取相关输入，复用同一财务领域算法，直接返回首屏指标/持仓/曲线及完整性诊断 | 消除236次请求及43MB首屏传输的结构条件；首次完整重算移到服务端后仍可能慢，必须测冷构建，不能仅测热进程memo |
| C. 持久、版本化首页投影 + 独立首页启动（推荐进入下一步验证） | 导入/成交修订、行情/FX/证据更新时建立或增量更新投影；完成后原子发布；打开时只读已发布且与当前版本匹配的首屏数据 | 对稳定数据、浏览器冷缓存和服务重启后的快速读取最有希望；增加失效、恢复、并发和写后读一致性复杂度。首次建模/未覆盖范围/缺外部数据仍无1秒保证 |

C是研究推荐，未批准或实施。可用A改善既有路径、以B验证算法与接口，再决定C的持久边界，避免一次大改后才发现投影口径不成立。无需更换SQLite或框架作为前提；目前证据没有证明换数据库能解决浏览器全量计算问题。

## 5. 推荐边界与必须保留的正确性

建议研究一个“首页读模型”公共模块：输入完整请求范围及要求的数据版本，输出四类指标、持仓、设计所需曲线、scope/selection、源revision、coverage/unknown原因和时间证据。它封装查询、领域计算、聚合与来源绑定；浏览器不再为了首页搬运全库行情。交易明细/回放仍通过对应按需入口读取。复用现有领域模块和已接受的金额合同/反例，避免服务端另写一套公式；现有已知财务错误必须保留失败反例，不能把错误结果固化为投影后称为等价通过。

必须满足以下条件，才能把读取结果计为成功：

1. **稳定数据身份**：交易导入/编辑/删除/回滚、instrument身份、账户别名、月结单/开仓与费用证据、Review/Recall依赖、行情补齐/修正及coverage、FX观测、交易日/市场时区/日历、算法/政策版本、币种/范围/附件筛选等实际依赖都进入revision或失效规则。不能用`count`、`max(updated_at)`、随机receipt、TTL替代完备变更身份；同数量修订和删后重建必须失效。
2. **原子发布与写后读**：输入快照、revision和投影绑定；构建期间发生更新要检测并重试或发布对应旧版本供明确历史访问。当前访问不可把旧投影声明为最新。跨接口行情与FX还需同样的版本协议；读事务内全量计算也可能加重阻塞。
3. **不伪造时间/新鲜度**：保留原始fetchedAt/knownAt/observedAt与asOf语义，新的readAt不能把旧报价/FX变新。当前“client-body-observed”的FX证据若改成服务器产生，须有明确版本化合同。日期切换、市场收盘和可知边界要触发正确判断，不能随意取整时间以提高命中率。
4. **缩小输入须证明等价**：账户费用、月结证据、历史FX资格、缺行情、未来交易、模拟隔离等可能影响筛选结果。未选证券可以从传输中移除，但完整性诊断不能漏；不可把现有`all-persisted-records/complete`收据贴到一个裁剪payload上。
5. **任意范围不能无限预计算**：账户子集、证券、期间、附件组合很多。可考虑分组事实与日期检查点，再按请求组合，但必须验证非加性指标、跨范围费用、期初状态和累计曲线，不能假定所有金额/收益率直接相加。64MiB缓存上限不因本次分析自动放宽。
6. **恢复与失败可见**：缺投影、schema/算法不匹配、缓存损坏、构建失败须明确诊断并走受控恢复；缺行情/FX要按既有规则输出unknown/stale。快速显示这些状态可以提高响应性，但不等于“真实财务已完整可用”门槛通过。

## 6. 对不同打开场景的判断

| 场景 | 1秒可行性判断 |
| --- | --- |
| 已启动服务、已发布最新投影、热访问 | 结构上有希望；需要端到端实测，当前未验证 |
| 同上，但浏览器模块/HTTP缓存冷 | 有希望，依赖首页独立产物、模块体积与真实首次hydration/图表成本；不能以热访问替代 |
| 服务重启、持久投影完整且版本一致 | 持久投影可以避免全部重算；须测启动后第一读、连接/迁移/缓存验证；若把进程启动计入，另行评估 |
| 投影完全丢失、算法升级、未缓存的任意组合 | 无法承诺；必须测真实非零多市场重建。当前只有零group来源成本样本，不足以支持上界 |
| 刚导入/修改后马上打开 | 取决于写入完成与投影发布协议。可把必要计算纳入提交完成条件，但需同时报告提交耗时，不能只将等待转嫁给用户后宣称整体更快 |
| 必须从外部provider补行情/FX才满足数据完整性 | 无法保证≤1秒；本地读取与远端更新拆开，并明确真实资料时点/缺失状态，不能将未知金额改为0 |
| `/trades`及进入交易/复盘 | 本轮未测。共享模块说明有受益机会，但需独立入口、筛选、分页、返回与回放性能证据 |

## 7. 一秒预算与可证伪验收

以下是**设计分配，未测量、非速度预测**。按保守串行边界记账，总计1000ms；未来若并行必须以关键路径而非相加报告：

| 不重叠边界 | 预算 |
| --- | ---: |
| navigationStart → 首份HTML完成 | 150ms |
| HTML完成 → 首页关键模块就绪并发出投影读取 | 200ms |
| 投影请求发出 → 完整body到达（含服务端版本检查、查询、编码、传输） | 200ms |
| body到达 → 小payload解析、来源/版本合同验证 | 100ms |
| 验证完成 → 首屏财务paint且控制可交互 | 200ms |
| 跨阶段调度/抖动余量 | 150ms |

应使用真实桌面1440×900、既有设计状态、同一隔离WAL一致数据库副本，锁定Node/SQLite/代码/算法版本与数据规模，建立生产预构建和开发两条基线。开发HMR性能单独记录。先测当前未插桩生产版本，再测候选，避免把插桩与冷编译收益算成业务优化。

最小判定旅程是：从地址直接打开首页 → 与当前源版本一致的指标、持仓和曲线真实显示 → 筛选/期间控制响应。记录navigation、TTFB、模块、projection版本检查/缓存命中/构建、SQL/映射、编码/bytes、body解析、合同验证、财务投影、React提交、实际paint/图表首帧、首个有效输入响应。每条记录使用同一request/generation关联，保留原始trace，不混用不同代或父子时间。

每种冷/热/失效状态重复采样并列出每次值、最大值和分位；任何已定义必测样本>1000ms都保留FAIL，失败或空财务也FAIL，不用平均值掩盖。建议先做小规模成对样本，再做至少30次/状态的稳定性观测；这不是对所有设备、无限数据规模的数学保证。

关键反例：无缓存重启；相同数量成交修订；导入/删除/回滚后立即返回；行情历史修正；FX日期与历史资格；账户别名及筛选组合；缺费用/缺行情；跨市场日历/时区边界；构建期间写入；断网/损坏投影；旧请求迟到；真实非零多市场与长历史数据。金额、缺失状态、来源/时点和曲线应与冻结的已接受领域oracle及金额合同作差分核验，辅以独立核算、含非零成交/持仓的业务金样；不能只复制当前存在已知失败的输出作为唯一正确答案，或只凭与旧实现一致证明财务正确。

候选变更最多3轮，由主代理独立验收；失败保留原因并暂停。性能、功能/状态安全、设计保真分别验收。历史曲线目前仍有`not-wired`、Bars及部分财务任务已达3/3暂停；它们未完成时不能宣称整页交付，分析通过也不恢复或重置这些任务。

## 8. 建议验证顺序

1. 冻结性能口径、数据与基线，补未插桩生产冷/热样本，建立真正可变红绿的端到端门槛。
2. 先做一个默认真实范围的“服务端紧凑投影 → 桌面真实指标/持仓/曲线”的最小旅程，验证算法和来源合同能否跨边界复用；暂不扩展全部组合。
3. 服务端窄查询/批量读取、首页启动拆分可按互不重叠文件并行；版本/失效协议先定，来源发布与消费接口不能各自假设。
4. 通过真实最小旅程后，扩展持久投影、失效/恢复、任意范围及写后读，逐项跑反例与1秒门槛；任何失败都保留，最终以整页旅程决定是否达标。

没有实施这些变更；本轮交付的是优化可行性与验证路径。分域证据见[服务端研究](SERVER-FEASIBILITY.md)、[来源模型研究](SOURCE-FEASIBILITY.md)、[启动研究](STARTUP-FEASIBILITY.md)；最终审核见[主代理验收](FINAL-ACCEPTANCE.md)。
