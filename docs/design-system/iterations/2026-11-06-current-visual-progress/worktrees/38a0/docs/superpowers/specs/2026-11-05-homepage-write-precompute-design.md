# 首页写后计算与旧库刷新：设计补充审查稿

日期：2026-11-05，更新于2026-11-06。状态：用户已批准方向；恢复第2轮接受既有契约，第3轮接受内存准备复用，第4轮接受可持久化的普通组当前金额及业务有效期接口。后台功能、真实全库及完整页面一秒仍未通过。

**结论：单笔写入与旧库批量刷新应共用一个计算模块；两个入口只负责确定哪些结果需要更新。** 原始文件用于验证导入，人工修正后的数据库用于核对已有事实。页面打开时只读取已准备的结果。

原性能任务保留[此前5/5失败记录](../../../.scratch/homepage-db-optimization-20261105/issues/01-execution.md)。用户回复“按照上述建议推进迭代”后恢复原任务，新阶段最多5轮；本稿不代表后台计算已完成。财务规则、Bars 开发和并发专项继续暂停；本稿仅设计等价计算的调度与结果存储。

## 一、目标与当前缺口

**目标是让计算发生在数据变化之后，避免页面打开时重复承担整库计算。** 缓存命中快，只证明读取路径可用；仍须证明单笔更新与旧库刷新能够产生正确的新结果。

| 项目 | 当前实现 | 本次目标 |
| --- | --- | --- |
| 写入后 | 更新全局修订号，旧结果失效 | 同一事务留下待更新记录，提交后唤醒后台计算 |
| 首次读取 | 没有缓存便等待完整计算 | 读取已发布结果；未准备好则明确显示处理状态 |
| 旧库补算 | 没有独立批量入口 | 扫描真实数据，按计算对象排队，共用单笔计算模块 |
| 更新范围 | 名称变化也可能使整套结果失效 | 区分展示信息与成交/估值依据，验证依赖后缩小更新范围 |

证据：[写后触发器](../../../app/lib/storage/homepage-view-store.ts)、[当前构建流程](../../../app/lib/storage/homepage-view-builder.ts)、[原验收记录](../../../.scratch/homepage-db-optimization-20261105/FINAL-ACCEPTANCE.md)。现有 `background` 选项只是预留，没有后台执行者。

## 二、测试资料如何使用

**两组文件与旧库承担不同角色，不用重新识别的内容覆盖人工修正。** 用户说明旧库来源一致、但 OCR 后做过人工修正；这是一条测试依据，文件与数据库逐条对应关系尚待核验。

| 资料 | 已核对事实 | 用途 |
| --- | --- | --- |
| `/Users/zhoulin/Documents/交易` | 207 份 PDF：A股目录9份、老虎69份、富途128份、重复副本目录1份 | 选择可核对样本，验证上传、解析、审核、落库、后台计算和读取 |
| `/Users/zhoulin/Documents/模拟交易复盘` | 6 份 UTF-8 CSV，原始行数合计130行；行数不等于成交数 | 验证模拟盘识别、单笔/单次导入和实盘隔离 |
| 现有业务库的一致性副本 | 包含人工修正后的成交和来源依据 | 验证历史批量刷新；核对计算前后的业务事实 |

实盘目录还包含脚本、日志与 SQLite 文件，测试入口只选明确的 PDF；模拟盘只选 CSV，不把整个目录视作待导入文件。测试原件只读，数据库写入使用显式指定的隔离副本。

每个选中样本记录文件摘要、来源批次、成交身份和人工确认字段。先按已存摘要核对；旧记录缺少摘要时，使用来源批次与行位置辅助核对，不能只凭文件名认定一致。无法唯一对应时保留差异并退出该样本的自动对账，不猜测修正内容。

测试分两条线：原文件走现有导入和人工审核流程；旧库直接从已确认事实重建结果，不重新 OCR、不重复导入成交。重复导入样本仍应被明确拒绝，不通过静默跳过制造“成功”。

两条线使用不同测试库：原件首次导入使用没有该导入记录的独立测试库；旧库刷新使用保留人工修正的一致性副本。不能把已导入同一文件的旧库副本用作“首次导入”成功样本。需要齐备行情/汇率的性能场景，在测试库提前准备对应本地资料并记录其版本。单笔算例用最小测试事实或正常修订入口构造，不截取文件后虚报整份导入完整。

## 三、共用模块与更新粒度

**共用的是实际计算与发布逻辑，不只是让两个入口调用同名包装函数。** 单笔变化要带上原有持仓和相关历史；不能把一条成交孤立计算为完整账户结果。

| 处理模块 | 输入与职责 | 输出与限制 |
| --- | --- | --- |
| 变更登记 | 与业务写入同一事务，记录变更对象、版本和原因 | 成交写入回滚时不能留下有效任务；写入拒绝不产生新结果 |
| 更新范围判定 | 根据变更前后账户、标的、市场、交易性质及依赖，确定受影响对象 | 修订归属时同时更新旧归属与新归属；未证明无关的依赖保守失效 |
| 共用计算模块 | 按固定输入版本读取受影响对象的完整必要事实，使用现有业务规则 | 输出持仓、回合和页面摘要依据；不添加第二套财务公式 |
| 结果发布 | 核对输入仍匹配，短事务保存结果并推进可读版本 | 失败保留此前成功结果及其版本；不能把旧结果标为最新 |
| 后台执行者 | 独立 Node 进程/worker 持有自己的数据库连接，顺序执行并合并待办 | 不在 HTTP 主线程通过 `setTimeout` 执行重计算；重启可恢复 |
| 页面读取 | 查询结果及准备状态，绑定当前请求与筛选条件 | 不调用完整构建器；处理中的状态不等于“当前没有交易” |

建议先以“账户＋标的＋交易性质”为基础计算对象，账户和市场汇总引用基础结果。收益率等不能直接相加的指标保留其计算依据；重复回合计数也必须按既有身份规则去重。具体物理拆表需在实施计划中结合现有 SQL 与来源校验逐项确定。

**普通组当前金额已通过局部复用验证，完整后台计算粒度仍须在产品接线中验证。** 现有构建器先处理全库事实和来源证明，再按范围生成结果。第4轮已证明可恢复局部基础金额，同时由原链路施加本次全库资格；没有绕过完整性证明。准备、历史及持仓仍每次执行，不能从本接口直接推出全链路已按组计算。若接线需要改动暂停中的财务规则或来源校验合同，记录阻塞，不能悄悄改口径。

| 变化类型 | 拟影响范围，须以等价测试确认 |
| --- | --- |
| 成交、撤销或修订 | 原归属和新归属的账户/标的/性质结果，以及引用这些结果的回合、账户、市场汇总 |
| 名称等纯展示字段 | 目录与展示结果；只有证明财务输入未变化，才复用财务结果 |
| 来源事实及账户映射 | 通过来源到成交/账户的关联找到影响对象；关联不完整时保守全量失效 |
| 行情或覆盖依据 | 引用相应标的、时间区间的结果，以及受影响汇总；不更改行情规则 |
| 汇率、报告币种、规则版本或时间截止 | 分别按实际依赖失效；首版不能可靠收窄时登记全量后台更新并如实计时 |

首次契约验证失败即不能进入“大规模拆表及全部调用方接入”，不得把依赖未证明当作实现细节留到最后。

不枚举预计算所有筛选组合。先存可复用基础结果，常用默认首页结果提前发布，筛选和分页通过这些结果查询；未覆盖筛选仍须实测，不能据默认首页通过便宣称全部通过。现有最多32个精确筛选缓存不作为基础计算模型的替代。

## 四、最小存储结构与数据流

**业务明细是事实，计算表是可重建结果，任务表记录还欠哪些更新。** 首版保持单机顺序执行，不引入分布式队列和并发调度专项。

| 建议对象 | 主要字段 | 关键约束与查询 |
| --- | --- | --- |
| 待更新对象表 | 对象键、目标输入版本、变更原因、任务状态、失败原因、实际尝试次数 | 对象键唯一；同对象连续变更合并到最新版本；按状态查待办 |
| 基础计算结果表 | 对象键、输入依据版本、规则版本、结果、生成时间、有效截止时间 | 对象和版本定位；保留可追溯依据，不携带重复的原始文件正文 |
| 页面已发布结果 | 范围键、结果版本、依赖版本、摘要、生成时间、有效截止时间 | 复用/演进现有结果表；发布指针与结果原子更新，不能混合新旧依据 |
| 批量刷新任务表 | 任务编号、范围、扫描位置、目标数、完成数、失败数、状态 | 可查询进度、取消后续排队、断点恢复；重复请求不重复建同批任务 |

字段与表名属于建议，不是现有 schema 声明。输入依据不能只有成交：现有计算所用来源修订、复盘、设置、行情、汇率及时间截止都须列入依赖；它们的规则保持原样。名称变更只复用财务结果，必须先证明其确实只影响展示。

单笔/单批写入流：

```text
现有审核与校验 → 提交成交及待更新记录 → 返回“已保存/处理中”
                                           ↓
                               后台领取 → 共用计算 → 原子发布
                                                           ↓
                                               首页读取新版本结果
```

待办必须随业务事务持久化；提交后的唤醒信号只是加速，不能成为唯一保证。服务启动时先恢复未完成任务，并核对旧库、过期结果、规则版本与时间截止，避免只有首次首页请求才触发计算。

待办登记设施应在服务启动、允许业务写入前安装并验证；不能等第一次首页读取才初始化。计算结果表自身的更新不得反向触发业务输入失效，避免后台任务循环生成任务。

计算读取一致的输入截面；重计算不持有长时间写锁。发布前检查依赖，已被新修订替代的候选不得发布为最新，保留最新待办再计算。这里只保证单机异步更新不丢失，不扩展到暂停的并发性能专项。

## 五、旧库批量刷新入口

**批量入口负责遍历和排队，不能另写一套财务算法，也不能通过重新导入旧成交完成刷新。** 对同一账户和标的的多条记录合并一次任务，避免1866条成交各触发一次整库计算。

建议本地管理接口：

| 操作 | 行为 |
| --- | --- |
| `POST /api/storage/read-model-refresh` | 校验明确的刷新范围；创建持久任务并立即返回202、任务编号和进度查询地址；请求内不遍历整库、不计算 |
| `GET /api/storage/read-model-refresh/:id` | 返回排队/处理中/成功/失败、进度、耗时和失败原因；不能把部分完成报告为全部成功 |

任务从校验后的服务器数据库连接读取数据，不接受任意文件路径、SQL或客户端提交的计算结果。刷新默认不更改业务事实。空库、无效范围、重复请求、部分失败和恢复行为须有明确回执。

同一计算对象无论来自单笔写入还是批量刷新，都进入同一计算函数、同一校验和同一发布事务。对比时固定输入版本与计算时点；同样输入产生相同业务结果，任务编号等运行信息不参与金额比较。

## 六、用最少案例验证关键分支

**先验证小案例的正确性，再用真实数据验证速度。** 以下是产品闭环用例；部分最小计算情形已有隔离探针证据，不代表后台或页面通过。相关修改模块的分支覆盖率目标仍为至少95%，当前工具缺失而未验证，不能靠增大样本文件替代边界覆盖。

| 用例 | 预期 | 要排除的错误 |
| --- | --- | --- |
| 买入100股，再卖出40股，无其他持仓事件 | 应余60股；相关金额按现有费用规则核对；发布后刷新仍一致 | 只计算新成交，丢掉此前持仓 |
| A股、港股、美股各一个最小样本 | 市场、币种与现有规则一致 | 因缺字段错归市场；跨市场错误相加 |
| 模拟盘买卖 | 只影响模拟盘结果 | 模拟成交混入实盘首页 |
| 人工修订金额或归属 | 采用修订值；必要时同时更新新旧账户/标的 | 重新解析覆盖人工修正；旧归属残留 |
| 同文件重复导入、非法写入、事务回滚 | 明确拒绝或回滚；成交和已发布结果不变化 | 拒绝后仍产生新结果或重复成交 |
| 写后立即打开 | 新版本完整显示时间单独测量 | 等后台16秒后才开始计时，伪称实时达标 |
| 单笔与批量作用于相同截面 | 同版本、同计算时点，业务字段逐项一致 | 两条入口使用不同算法；仅比较数量 |
| 计算失败、中断重启、计算时输入更新 | 失败可见、待办可恢复；不发布不完整/已过时结果 | 把旧缓存标为最新；丢失待办 |
| 空库、首次补建、结果过期或损坏 | 状态明确、可重建、无“空数据”假结论 | 仅已有缓存时测试通过 |
| 后台计算期间访问已准备页面 | 读请求正常响应；记录实际耗时 | 重计算占用主线程，其他访问仍超时 |

正确性对照有两层：手工可算的最小买卖案例验证业务含义；固定时点的旧库全量结果与单笔更新/批量刷新结果对照验证等价。只比较同一函数调用两次，不能独立证明业务正确。

## 七、性能验收与取舍

**后台化先解决“谁承担计算”，局部重算才解决“每次要算多少”。** 若每笔写入仍后台全库计算16秒，写后立即打开的实时目标依然未通过。

| 场景 | 必须记录 | 通过条件 |
| --- | --- | --- |
| 旧库首次补建 | 排队、扫描、计算、发布总耗时，数量/金额/缺失状态对账 | 可恢复且结果正确；构建时间单独报告 |
| 已补建后的冷/热访问和服务重启首读 | 页面完整可见时间、查询耗时、字节量 | 本地数据齐备，完整首页≤1秒 |
| 单笔/单批写入后立即打开 | 从提交成功到新结果完整可见的总时间，含等待后台时间 | 按原修订后首读边界验收；超1秒明确FAIL |
| 已知缺失行情/汇率等 | 缺失原因与可用内容，不添加虚构结果 | 保留现有语义；不把缺失状态算成完整数据达标 |
| 筛选、分页、交易库返回 | 对应最终版本的功能与桌面浏览器证据 | 单独验收；不借首页缓存命中替代交易库一秒目标 |

建议统计口径：功能与等价用例先通过；每个性能场景至少20次独立测量，保留全部原始样本，报告P50、P95、最大值和超1秒次数。首批20次的P95取排序后第19个样本；为忠实执行当前“1秒硬门槛”，任一超过1秒的必测样本即标记该组FAIL，不用平均值掩盖。重启、写后首读各自重新构造条件，不把连续缓存命中重复计为冷访问；单次结果仅作定位证据，不能证明长期95%请求达标。这是本稿提出的有限样本验收方法，不是既有统计结果。

取舍：仅后台执行整库构建可作为接线对照，但不能独立交付实时目标；推荐“共用局部计算＋持久待办＋原子发布”，与用户提出的双入口方向一致。纯定时刷新无法保证刚写入的数据及时就绪，不作为主更新机制；时间截止刷新只补充没有用户写入时的变化。

## 八、实施前需要确认的边界

**本稿先补齐设计与测试依据，原暂停记录保持有效。** 恢复时必须沿用原问题及旧失败记录，明确新授权轮次，不通过新建任务绕过5轮上限。

恢复后的首条验收应是：在未导入该原件的独立测试库中完成一次真实来源导入，经审核写入后后台实际计算并落库，桌面首页读取该新版本，返回与刷新仍一致；另用最小单笔算例验证局部更新。该闭环通过后再扩大到保留人工修正的旧库副本全量刷新；原始资料与业务库不做试验性覆盖。

拟由 Sol 6.1 Ultra 承担有明确文件范围的实施，Luna 6 Max 独立审查，协调者完成实际接受。实施计划应单独列出后台执行者和真实调用方，避免再次只实现缓存、没有人接入写后计算。

独立设计审查：[审查结论与处置](../../../.scratch/homepage-db-optimization-20261105/precompute-design-review.md)。审查不等于代码、性能或产品验收；依赖粒度的可行性仍须按上述首项门槛实测。

## 九、前置调查历史：第2轮契约与第3轮准备复用

**恢复第2/5轮接受的是前置调查，不是“局部重算已成立”。** 两名Sol分别构造真实计算及来源探针，各有独立Luna审查，协调者重跑8项通过。当前全量入口可处理分次和批量写入后的相同事实；但B账户来源缺口能改变A账户合计资格，不能直接缓存A结果后跳过全库校验。
