## Implemented

- Exported `RecoveryPrototype` and `RecoveryPrototypeProps` as a pure controlled UI module. `bulk` phase/progress, interruption, excluded/lagging bounds, checkpoint state, current portfolio, and demo arms all arrive as props; controls call only the runtime callbacks. The idle action opens a consequence-first confirmation, progress displays the supplied completed-day count and stop action, and errors/lagging feedback stays separate from the time controls.
- Confirmation explains that remaining market data through the planned end and the portfolio result will be shown, that expanding can stop on a complete day, and that returning to process review preserves the seen-future marker. Both Cancel and Escape call the runtime cancel action and return focus to the “展开剩余行情” entry. The Escape handler stops propagation; runtime still needs to suppress its global advance shortcuts while `phase === "confirming"`.
- The collapsed demo section labels its synthetic, in-memory boundary. It exposes one-shot data interruption/execution failure controls with the armed portfolio/date shown separately from the currently selected portfolio. Partial/unfilled execution has its own locked `{kind, portfolioName, date}` arm; switching tabs does not relabel the armed target. Partial/unfilled choices disable when there is no next planned execution date.
- Checkpoint controls say “memory” throughout. A simulated save failure leaves the prior saved date visible, exposes retry, and keeps reloading the previous checkpoint available when one exists. The copy distinguishes this from browser persistence and states that seen-future exposure remains.
- Extended the result boundary contract with optional `resultBoundary: { kind, maxDate }`; an excluded portfolio can display its frozen last-complete date even when global expansion continues. Stage and complete labels are based on the visible R and portfolio boundary, not the global planned end.
- Result analysis uses only actual `trades` for FIFO accounting, trade count, turnover, realized/unrealized contributions, and rebalance counts; an `unfilled` event is explicitly excluded from executed-trade accounting and rebalance totals. Partial events count as actual execution using their supplied actual trades. Results show planned versus actual counts, execution notes, visible partial/unfilled status labels, and separate filters. Existing R-prefix, entry ID, scroll/filter retention, and event return callbacks are preserved.
