# 首页数据库与性能设计：独立专家审查

日期：2026-11-05。审查对象：[首页数据库结构与读取设计](homepage-database-design.candidate.md)。审查视角：SQLite 数据建模、查询与索引、财务数据正确性、网页首屏性能。独立 Agent 只读核对了设计、相关字段对照和既有实验，并查阅 SQLite 与网页性能官方资料；本次没有运行新的性能实验，也没有修改数据库。

**后续业务决定：**用户已明确：实盘同一证券跨所选账户按交易时间合并到同一标的；不同计算时点的币种换算统一取最新汇率。下文保留原审查记录，其中将这两项列为待决及以不同时点汇率举例的内容已被此决定替代。数量、成本、更新和重算的具体实现仍需设计验证，详见[更新后的设计稿](homepage-database-design.candidate.md)。

## 1. 结论

**方案方向合理，可以作为讨论稿和实验方向；目前还不能作为直接实施的数据库合同，也不能保证完整首屏达到 1 秒。** 建议继续采用“保存原始事实、提前计算可重建结果、按需读取”的方向，但应先确定业务口径、结果版本和代表性查询，再通过真实数据实验判断具体表与索引。

| 维度 | 审查结果 |
| --- | --- |
| 分层和拆表方向 | 合理：成交事实、持仓、每日结果和已平仓回合有不同粒度，分开有利于复用和追溯。 |
| 字段完整与业务规则 | H01–H32 已列需求，但账户身份、回合、筛选、币种与累计规则仍有待决项；不等于字段已可直接建表。 |
| 索引 | 候选索引适合做实验；不能断言所有账户组合、排序及搜索都会用到索引。 |
| 结果更新和一致性 | 有方向，仍须补充版本切换、跨范围读取和失败恢复的可执行合同。 |
| 1 秒目标 | 四类场景均**未验证**：冷/热访问、服务重启后首读、导入或修订后首读。 |

## 2. 优先解决的问题

**以下是设计缺口或待验证风险，不表示它们已经在运行产品中复现。**

### P1：页面需要的字段还不能全部落成表结构

**具体问题：** [首页设计的字段和 32 项控件清单](homepage-database-design.candidate.md#10-补充汇率证据累计边界与逐控件核对)标出了需求，但有些字段的业务含义未确定。例如同一证券在两个账户中分别持有多头和空头时，是否合并为一行、成本和排序如何计算，还没有定案；待复盘状态究竟属于成交、回合还是证券也未定。

**影响：**即使建出表和索引，也可能得到不能正确筛选或容易误导的数字。先为每个关键控件补齐“展示值 → 具体来源字段 → 计算规则 → 缺失状态 → 筛选影响”的对应表，并用跨账户、多空、缺资料等小例子核对，再确定唯一键和表字段。[现有字段对照](view-field-mapping.candidate.md)已将这些缺口标为未核实。

### P1：新旧结果如何切换尚不足以保证一致

**具体问题：** [发布和恢复设计](homepage-database-design.candidate.md#54-计算发布与恢复)提出检查依据后发布，但尚未定义检查与发布的事务边界、多个范围如何使用兼容版本，以及旧版本何时可回收。

**例子：**系统算完旧数据，检查后用户又修订一笔成交，如果仍发布刚算出的旧结果，首页会把旧数字当新数字。翻页期间发布版本或回收旧版本，也可能出现第一页和第二页不一致。

**建议：**在同一事务中比较输入版本并有条件地发布；明确摘要、列表、翻页和导出怎样固定兼容版本及过期后如何处理，并测试失败重试和重启恢复。SQLite 的一致快照只对同一次读取事务有效，跨请求不能仅凭这一点保证一致。[SQLite 隔离机制](https://www.sqlite.org/isolation.html)

### P1：历史曲线和币种需要更精确的依据

**具体问题：**[汇率与累计边界补充](homepage-database-design.candidate.md#10-补充汇率证据累计边界与逐控件核对)已指出要区分原币和报告币，但换算适用时间、日历覆盖和历史回补规则尚未确定；已平仓回合的原币、报告币和换算证据也需完整定义。

**例子：**一天两笔美元平仓如果按业务规则使用不同时间的汇率，先将两笔美元金额相加再统一换算可能得到不同结果；某证券期间开仓又清仓时，某天没有结果行，也不自动证明那天持仓为零。

**建议：**明确每个指标使用的成交时点或估值时点、汇率方向与来源，保留可用和缺失状态；建立开仓、平仓、无交易日、历史回补及缺价/汇率的小样例，逐日与完整重算对账。具体业务汇率规则仍需决定，不能直接套用本例。

### P1：数值精度需要落到可执行规则

**具体问题：**“精确数值”和“无损整数排序”还没有规定各字段的小数位、数值上限、乘法与汇总上限、舍入和溢出处理。数据库、服务和浏览器使用的数值表示也可能不同。

**例子：**大金额乘汇率或多账户汇总可能超出整数范围；JavaScript 的普通数字无法精确表示所有超过 2⁵³−1 的整数。不能为了排序速度悄悄截断金额或使用近似值。

**建议：**先定义数量、价格、汇率和金额的精度与范围，说明跨层传输格式、计算时机、舍入及不可表示时的处理，再用边界值对账。[SQLite 浮点说明](https://www.sqlite.org/floatingpoint.html)、[SQLite 聚合函数](https://www.sqlite.org/lang_aggfunc.html)

### P1：目前没有证据证明完整首页能在 1 秒内显示

**具体问题：**[现有实验](../../.scratch/page-reading-mvp-wayfinder/homepage-precomputed-read-analysis-2026-10-29.md)中的 0.677 毫秒是进程内读取精简事实，不包括完整财务、曲线、HTTP 和浏览器；首次准备精简事实约 7.3 秒。它支持继续实验，不是完整首屏成绩。

**建议：**用隔离数据库和桌面浏览器，定义“完整且正确”的所有首屏区域，对冷/热访问、重启后首读、导入或修订后首读分别计时，记录准备、数据库查询、接口大小、网络/解析和渲染时间。导入后更新尚未完成或显示旧数据，不能算通过。

业界常见的 LCP 指标测量最大可见内容何时出现，可辅助定位加载，但**不等同于本项目要求的所有首页组件及数据完整正确**。[web.dev：Largest Contentful Paint](https://web.dev/articles/lcp)

### P2：候选索引是否有效，需要针对真实查询证明

**具体问题：**[候选索引](homepage-database-design.candidate.md#6-索引准备怎样查而不是越多越好)在版本、性质、市场、账户均能有效限定时可能有帮助；全部市场、多账户、证券下钻或搜索使用的条件不同，不一定能提供所需顺序。

**例子：**两个账户持有同一证券，页面先合并两个账户的市值再排序；单账户的市值索引不能直接提供合并后的排序结果。`(version_id, position_key)` 能按键查找或按键排序分页，并不能支持任意金额排序分页。

**建议：**用真实数据分布分别测试单/多账户、全部市场、日期与证券下钻、搜索、聚合排序；记录实际 SQL、`EXPLAIN QUERY PLAN`、是否产生临时排序、冷热耗时，与无索引情况对照，再选择索引。多列索引如何被使用取决于查询条件和列顺序。[SQLite 查询规划](https://www.sqlite.org/queryplanner.html)、[SQLite 查询计划说明](https://www.sqlite.org/eqp.html)

### P2：提前计算也有写入和存储代价

**具体问题：**按账户、证券、日期和版本保存结果，并叠加多个索引，会增加构建和更新工作；历史补录可能影响该日之后的很多结果。

**建议：**测量首次构建、历史补录、行情/汇率更新的耗时，以及数据库、索引、WAL 日志和检查点的增长；设计旧版本保留与清理，再决定是否增加日/月聚合表。SQLite WAL 允许读写并行，但同一时刻仍只有一个写入者；性能影响取决于实际负载。[SQLite WAL](https://www.sqlite.org/wal.html)

## 3. 建议的审查与实验顺序

1. **对齐业务口径：**先拿跨账户、多空、回合、期初、缺失和汇率的具体例子确认应显示什么。
2. **补全表和读取合同：**给每项关键控件标明来源、字段、粒度和状态，明确版本、发布、翻页及失败恢复。
3. **隔离实验：**按真实数据分布构建少量候选结果和索引，逐项对账，再量查询、写入、空间和重建成本。
4. **桌面首屏验收：**四类场景分别记录完整链路，以正确完整首屏 ≤1 秒为目标；未达到时指出具体耗时环节。

财务与 Bars 开发任务仍按此前决定暂停；本文不授权恢复实施，也不把审查结论当作产品验收。
