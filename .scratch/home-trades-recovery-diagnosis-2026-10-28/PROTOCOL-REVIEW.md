# 首页与交易库：读取协议和分页设计审查

日期：2026-10-28。性质：现状诊断与待验证设计建议，不代表代码修复或整体验收通过。

## 核心结论

首页持仓表每次展示 8 行，但这只是浏览器拿到全部数据之后的显示分页。当前首页接口按“交付全部原始数据供浏览器验证、重建和计算”设计，不是“交付页面摘要和当前页”设计；交易库也使用这条来源读取链。这个边界是 34 MB 响应的主要设计原因，值得优先改造。完整性校验有其用途，但首页展示不应天然要求把整套原始材料反复传到浏览器。

本次检查的是 3333 服务使用的隔离副本，包含一条先前测试成交；不能把其具体数量当作正式数据库统计。没有改业务数据库或产品代码。

## 用户看到的一页，和系统实际读取的一页不是同一回事

以本次副本为例：存储中有 1,867 笔成交、236 个标的；首页持仓表一页最多 8 条持仓行。成交、标的和持仓行是不同概念，不能直接把这三个数字相减。

目前流程：

1. 服务从数据库取得全量数据，把成交按每 1,000 笔拆成内部数据页；随后又把所有内部页合并到一次 HTTP 响应。每个内部页还带来源材料和校验信息。
2. 浏览器收到完整响应，校验整个响应和每个内部页，再重建交易集合、计算页面结果。
3. 首页在浏览器里过滤、排序后，只截取当前的 8 条持仓行显示。

证据：[服务拼装全部页](../../app/lib/storage/homepage-source-snapshot.ts)；[浏览器读取和重建](../../app/components/trade-review-workspace.tsx)；[首页显示分页](../../app/components/homepage-v25/home-surface.tsx)；[验收用的持仓列表分页规范](../../docs/design-system/baselines/2026-10-22-homepage-v2.5/source/visual-design.candidate.md)。交易库也有显示分页，但同样从该完整来源开始读取。

## 实测：34 MB 都装了什么

2026-10-28 本地请求返回 34,332,057 字节（约 34.3 MB，十进制），HTTP 200。下面是实际响应中字段的 JSON 编码大小，子项属于父项，不能把所有行相加。统计只保存字段名、大小和数量，不保存交易内容。完整统计见 [protocol-fields.json](protocol-fields.json)，测量代码见 [protocol-fields.mjs](protocol-fields.mjs)。

| 位置 | 实测大小 | 含义 |
|---|---:|---|
| bootstrap | 约 6.33 MB | 旧式启动集合；其中成交约 3.24 MB、行情任务约 2.68 MB，另有导入历史、标的、复盘状态和设置等 |
| tradeReadPages | 约 28.00 MB | 两个内部成交页及其展示对象、来源材料和校验信息 |
| 每个内部页的材料现状 materials | 各约 4.34 MB | 两页完全相同，共出现两次 |
| 每个内部页的材料沿革 materialHistory | 各约 4.37 MB | 两页完全相同，共出现两次；它和材料现状是不同概念 |
| 每个内部页的诊断 diagnostics | 各约 0.11 MB | 两页完全相同，共出现两次 |
| 两页 facts 中的 rawEvidenceJson 和 evidence | 值合计约 5.48 MB | 原始证据的 JSON 文本及其解析对象均被放在成交事实中，作用与保留必要性需逐项核查 |

仅对这份样本而言，第二页中上述三类与第一页完全相同的内容合计约 8.82 MB；这不是承诺可以直接删除的数量，也不代表全部重复都已找出。两页 display 中再次包含各页成交、完整标的和导入历史；bootstrap 也包含成交和相同的标的、导入历史。来源材料的存在及材料沿革的业务作用不能因为大小就否定，应按用途和字段分别核查。

数据取得和分析统计本次合计约 7.4 秒，包含脚本解析和统计开销，不是浏览器首屏耗时，也不是独立网络传输耗时。先前 Node 分段测量见 [contract-breakdown.json](contract-breakdown.json)；此前桌面实际超时证据见 [CONTINUATION-2026-10-28.md](CONTINUATION-2026-10-28.md)。现有数据支持这是主要瓶颈之一，不足以计算每一步对完整首屏耗时的精确占比。

## 问题树与判断

### Q01：页面所需对象与接口交付对象不匹配

首页需要当前筛选范围的总体摘要、当前页持仓及交互所需状态；接口却明确要求完整枚举所有已保存记录，包含启动集合、全部交易读取页、复盘摘要和凭据。其设计适合完整来源重建，粒度不适合页面首屏。交易库复用同一大接口，尽管交易库场景跳过了行情与汇率请求，仍需读取和处理交易全集。

证据：[响应类型与完整范围](../../app/lib/storage/homepage-source-contract.ts)、[首页与交易库共用读取](../../app/components/trade-review-workspace.tsx)。

### Q02：分页发生在传输之后

底层存在每 1,000 笔的内部成交分页，但服务端循环读取所有页，最终一次交付；首页再在客户端按每页 8 行切片。因此不能称为没有分页，更准确是“没有针对首页持仓结果的按需传输分页”。交易库列表也在得到集合后切片。

证据：[全部内部页装配](../../app/lib/storage/homepage-source-snapshot.ts)、[首页 8 行切片](../../app/components/homepage-v25/home-surface.tsx)、[交易库列表切片](../../app/components/library/trade-library.tsx)。

### Q03：校验材料与展示数据捆绑，且存在重复编码

原始证据、材料现状、材料沿革、诊断、展示投影同时出现在响应中；本次两个内部页重复整套材料。响应和每一页都有内容摘要，浏览器还会先复制并校验全部内容。校验能发现传输或结构不一致，但校验成功不等于历史完整、财务金额可计算；不能通过关闭摘要或删字段来绕过既有合同。

证据：[成交事实同时装入原始及解析证据](../../app/lib/storage/stored-trade-snapshot.ts)、[客户端完整响应与各页校验](../../app/lib/storage/homepage-source-contract.ts)。

### Q04：浏览器需要等待全集和计算，导致 8 行仍可能很慢

需要的工作不止下载：服务端构造多个内部页并计算摘要，浏览器再解析、复制、校验、重建、筛选和计算。这一设计也解释为什么仅在页面上增加翻页按钮无法解决超时。优化空间包括读取范围、传输体积、计算位置和校验粒度，必须分别测量。

### Q05：轻量分页若设计不当，会制造错误数字

首页总额和统计必须依据当前筛选范围的完整有效数据，而不是只汇总当前 8 行。例如账户下有 20 条持仓，第一页只展示 8 条，但总市值应对应符合条件的全部 20 条；其中有无法可信计价的项目时，应遵循现有缺失规则，不能悄悄当作零。期间计算可能需要之前的成交或可信期初依据，不能只取期间内几笔就声称持仓或收益完整。

搜索、排序和计数必须面向完整筛选结果，然后分页；导出仍须包含完整筛选结果，不能只导出当前页。跨页应保证同一业务版本，数据在翻页之间变化时应明确刷新或重新读取；行情、汇率、复盘的更新状态也需各自表达，不能用成交版本代替一切。

证据：[持仓搜索排序与导出规范](../../docs/design-system/baselines/2026-10-22-homepage-v2.5/source/visual-design.candidate.md)；[数据库模块候选稿的前序依据和版本规则](../../docs/backend-design/database-module-design.candidate.md)。后者是待审设计，不应误写成已经实施的承诺。

## 建议的接口职责与验证

以下是设计方向，具体字段及计算方案仍需单独设计、验证和决策：

1. 首页摘要读取：按市场、账户、期间等范围提供总体统计、可用性及相关版本；金额未知、数据不足和真正为零要区分。
2. 首页持仓列表读取：提供当前筛选排序后的当前页、总数、页码或游标及所需展示字段；详情和追溯按需读取。总数及摘要从全范围计算，不能从当前页推算。
3. 交易库读取：提供其自身的标的／回合列表和范围汇总；展开详情时再读取相关成交与必要来源，不能强制先下载首页财务原始全集。
4. 校验和追溯：原始来源、历史材料和逐条诊断仍可查；在产生页面结果的地方建立等价的校验、版本绑定和失败状态，保留可追溯依据。不能把存储完整误称为财务完整，也不假设每条记录都需要相同材料。
5. 性能实现选择：比较数据库窄查询、请求时计算与在数据更新时生成并持久保存可验证结果；检查写入、导入修订后的原子更新与失效、重启恢复和首读。仅缩小响应不证明计算本身能在 1 秒内完成。

验收应覆盖：桌面实际首屏完整展示；首页和交易库各自冷／热访问、服务重启首次读取、导入或修订后首次打开均在本地数据齐备时 1 秒内；搜索排序分页和导出覆盖完整结果；版本变化、证据不足、数据损坏时不把错误结果显示为零；页面展示和明细追溯与权威数据核对。外部行情或汇率补齐与进程启动按先前约定单独计时。还需测量新协议真实响应字节数和服务、网络、浏览器各环节耗时。
