# 首页读取优化：本轮实现与验收边界

本轮将首页需要的展示结果留在服务器数据库中，避免每次打开都传输和计算完整交易材料。**这解决重复打开的重算，但首次生成和输入更新后仍需重建；是否达到一秒，必须分别测量这两条路径。** 最终结论以[本轮验收记录](../../.scratch/homepage-db-optimization-20261105/FINAL-ACCEPTANCE.md)为准。

## 1. 页面到底需要什么

首页需要账户与证券目录、当前期间的汇总和曲线、持仓摘要。原始成交、原始材料、完整行情、逐个交易日的诊断记录，不应随首页摘要一起返回。

|使用位置|本轮返回内容|留在服务器的内容|
|---|---|---|
|市场、账户与证券搜索|账户名称、证券身份及去重后的搜索名称|完整成交及重复名称|
|汇总、曲线与说明|原有精确金额、可用状态、缺失理由、展示所用证据|内部逐笔计算账本、界面未使用的缺行情日期清单|
|持仓表格与详情|现有持仓行、汇总、证券身份和可用状态|构造持仓所需的完整成交材料|
|进入交易库、导入或修复|真正需要时再准备原有完整工作区|不为首页提前加载该工作区|

展示摘要只是供界面使用的结果，不能反过来当作财务事实参与校验。缺失金额仍然缺失，不能改成零。

## 2. 数据分成哪些层

业务事实表继续保留，本轮不把成交、行情和复盘合成一张大表，也不改原始数据。新增三张可丢弃、可重新生成的结果表。

|表|一行代表什么|主要字段|主键 / 查询依据|
|---|---|---|---|
|`homepage_view_input_state`|当前整本账的首页输入修订号|`singleton`、`epoch`、`revision`|固定主键`singleton=1`|
|`homepage_view_catalog`|某一输入版本的账户和证券目录|`input_version`、`payload_json`、`digest`|固定主键`singleton=1`，读取时核对输入版本|
|`homepage_view_results`|某个市场、账户、期间和筛选范围下的完整展示结果|`cache_key`、`input_version`、`result_version`、`algorithm_version`、`business_day`、`selection_json`、`payload_json`、`digest`、`built_at`、`valid_until`|联合主键`(cache_key,input_version)`，先定位一行再核对有效期|

`payload_json`是已经算好的页面摘要，不是原始大文件。金额保持原来的精确字符串；`digest`是内容指纹，用来发现损坏；`result_version`与该指纹绑定。主键本身已有定位索引，不能靠另建一张“索引表”替代正确的查询设计。[查询计划与解析计时](../../.scratch/homepage-db-optimization-20261105/read-model-audit.json)单列提供，不能把这段毫秒级查询等同于整个页面时间。

## 3. 写入、计算与读取怎样衔接

写入先使旧结果失效，计算成功后才发布新结果。现在实现的是**按需生成后持久复用**；独立后台预计算、写后自动发布及启动预热尚未接入，不能称为已完成异步更新。

1. 成交、证券、行情、汇率、复盘等依赖表发生写入时，同一数据库事务中的触发器增加输入修订号；账本身份和账本版本也进入输入版本。
2. 首页先读轻量目录。读取指定范围时，使用输入版本、算法版本、业务日期和筛选条件定位结果。
3. 结果仍有效时直接返回摘要，并绑定本次请求标识；不复用旧请求的身份。
4. 没有有效结果时，服务器沿用现有来源校验、财务计算和持仓规则生成结果。计算在请求内等待，这就是本轮尚需实测的慢路径。
5. 发布时再次核对输入版本、业务日期和有效期；任何一项变化均拒绝发布，避免旧计算冒充最新数据。损坏的结果重新计算，不直接采用。
6. 成功发布时清理旧版本、旧算法、过期结果，并对剩余选择结果设定数量上限。未来自动更新器应复用相同发布门槛。

有效期不能只按固定分钟数设置。本轮沿用既有市场日历，取下一次成交/持仓事件、市场日期或已完成行情边界等变化点，并设置最长24小时上限。

## 4. 本轮做了哪些等价优化

优化只消除重复工作，不放宽完整性规则。相同对象在一次编码或一次计算内复用；每次新读取都重新核对，避免修改后的数据沿用旧指纹。服务器采用与浏览器结果一致的原生SHA-256；持仓数量采用窄读取，避免为了展示数量重复计算不需要的费用明细。所有改动都保留未知状态和原有金额语义。

另外修复了一个真实输入错误：月结证据附着后的成交对象，与后续来源校验使用的成交对象不一致。现在同一条计算链使用同一批已准备的成交；没有绕过校验。

## 5. 如何判断有没有成功

必须同时看正确性和耗时。缓存命中快、接口200、骨架消失、未知数字显示为横线，都不足以单独证明完整首页达标。

|场景|必须包含的时间与检查|
|---|---|
|浏览器冷、热打开|页面资源、目录、结果传输、解析、React更新和实际绘制|
|服务进程重启后的首读|验证结果持久化，不借用上个服务的内存|
|数据修改后的首次打开|必须使用新版本，不能拿旧结果或“更新中”冒充通过|
|没有有效结果|单列首次生成时间、各阶段时间和实际返回字节|
|界面正确性|桌面持仓、搜索、筛选、详情、分页、期间与交易库往返；独立对照V2.5视觉稿|

原始行情不足、既有终身收益来源资格未接入、历史区域尚未接线，分别记录原因，不混为“数据库没有数据”。财务资格规则和Bars开发继续暂停。若完整首屏仍未达标，应保留失败与轮次记录，而不是把重复读取的好成绩扩大为整体成功。
