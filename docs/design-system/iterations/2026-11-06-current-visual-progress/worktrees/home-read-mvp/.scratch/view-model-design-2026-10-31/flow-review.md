# 数据模型候选稿独立审查：身份、导入、异步与性能

审查对象：[`view-driven-data-model.candidate.md`](../../docs/backend-design/view-driven-data-model.candidate.md)，按审查时磁盘上的 227 行版本（含 5.1–5.4、双截止动作表、依赖向量及单事务 CAS 发布条款）。  
依据：本目录 [`replay-import-evidence.md`](replay-import-evidence.md)、[`home-trades-evidence.md`](home-trades-evidence.md)、[`current-model-evidence.md`](current-model-evidence.md)。只读审查；未读取数据库、运行服务或执行 UI/性能测试。

## 结论

本轮最新稿显著补齐了上次讨论的核心方向：5.3 明确区分行情与成交截止，并要求快照绑定两种截止、来源时间精度及未来可见状态；§6 列出完整依赖版本向量、同库事务内比较与切换、跨库/外部源限制，以及请求幂等、重算中再次修改、重启和翻页版本切换的处理。5.1 对页面字段的推导也更具体。就候选模型的逻辑表达而言，**双时点回放和相容版本读取现已基本覆盖**，不再列作阻断发现；实现是否满足仍未验证。

仍需处理两类设计缺口：实盘/模拟账户、practice、simulation run、round 的稳定身份映射仍明确待定；异步更新虽然表达了“可恢复、幂等、不漏变更”的结果要求，但没有说明变化如何被任务安全消费/合并，尚难按竞争时序确认不会丢变更。导入来源与提交链条已列出主要对象，但链接基数和计划/回执所绑定的输入版本还应说清。1 秒目标有正确的限制说明，验收协议仍不够可复现。

## P1 — 账户、practice、simulation run、round 的稳定身份映射仍待定

**事实。** 候选稿第 83 行新增账户 ID 与来源映射，并明确名称不是身份；第 93–94 行将 practice、run、round 拆开。但第 93 行仍称 practice 与运行身份，第 94 行仍称稳定身份规则待定。现有计算以 account + instrument + nature + simulation run 为业务组；来源证据指出，当前四份 TradingView 文件归同一个模拟账户，旧规则又按不同内容划 simulationRun，而交易库要求同一练习可含多个回合、同标的同日的练习相互独立。候选模型尚未明确这些对象之间的身份及关系边界。

**反例。** 若按文件/批次分配账户或 run ID，同账户四份文件被拆成四组；若按 account+symbol+date 合并，同日重复练习被合并；若把 practice、run、pair/round 共用一个 ID，一个练习内多个回合会串联。账户显示名称相同也不构成跨账户身份或判重依据。

**建议。** 在逻辑合同中先定稳定身份关系，再定物理键：账户规范身份与材料范围内的来源账户标签映射分离；practiceId 独立于账户、文件、证券日期；声明一个账户可有多个 practice/run、一个 practice 可含多个 round，以及 run 与 practice 的兼容/迁移规则。身份未知时保留 unresolved，不靠文件名或日期猜测。若旧 TradingView run 与当前 practice 定义尚不能统一，将其明确作为待确认输入，阻止据此定唯一键/汇总范围。

**证据。** `current-model-evidence.md` §2、§4；`replay-import-evidence.md` §4、§7 第 1 项；`home-trades-evidence.md` §4 T-02/T-09/T-10；候选稿第 83、93–94、133 行。

## P2 — 异步任务要求已写明，但变更消费水位和合并竞态未定义

**事实。** 最新稿已有变化记录与更新任务（第 101–103 行）、同事务写入待处理记录（§6.1）、完整依赖向量 CAS（§6.4）、旧任务拒绝重排、同 request ID 查回执、幂等重试和暂存/发布指针分离（§6 矩阵）。这些覆盖了主要结果状态。尚未定义任务从变化记录中领取/合并工作的边界，以及“标记完成”的水位或条件；“合并影响范围”“不能漏变更”仍是目标描述。

**反例。** 工作者读到 dirty 范围后，另一写入追加变化；若工人完成时清整条 dirty 状态，第二个变化被吞。一个变化在任务合并后、发布前到达，可能未进入当前输入而又被误标已消费。任务发布后、任务完成状态落库前崩溃，也需要幂等地发现发布已成功，而不能重复累加或丢弃后续工作。

**建议。** 不必先决定具体队列产品，但应定义可审计的消费协议：变化序号/generation；任务绑定开始与完成水位、输入依赖向量、影响范围；并发变化推进水位且并入范围时不得被旧任务清除；领取/租约过期和重试状态；“发布完成”和“哪些变化已消费”的原子关系。把上述竞争反例纳入后续隔离库故障验收。候选稿目前已声明幂等和恢复目标，缺的是令它们成立的逻辑状态转换。

**证据。** `current-model-evidence.md` §6、§7 明确将异步丢唤醒、跨进程 CAS、崩溃恢复列为未验证；候选稿 §6 第 183–203 行。

## P2 — 导入链已拆分主要对象，但来源链接与审核计划输入绑定仍需明确

**事实。** 最新稿第 85–90 行及第 105 行已区分批次、材料版本、来源观察、审核计划/回执、成交、修订/撤回，并分开预览与实际结果；这能表达来源细节与文件不等于成交。剩余不足是来源观察与成交关联的基数/属性未明确；计划 ID/请求 ID与材料版本、账户身份范围、book revision/input digest、choices/reasons 的绑定也没有落到逻辑表关系上。第 105 行将冲突/重复判定留给单独任务是合理边界，但本模型仍须保留该任务需要的证据。

**反例。** 一条来源观察可能是多条规范成交的证据，一条成交也可能由多个来源材料佐证；若实现为单向外键，会丢一侧来源。完全相同的两行可能是合法两笔成交，不能按内容去重；完整材料版本中某行缺失时，必须能区分保留、撤回或未表示。审核计划基于旧 book revision 生成后，重试/提交时若没有绑定其输入版本及用户选择，可能应用过期 choices 或重复提交。

**建议。** 在逻辑模型明确 source observation↔execution link 为可追溯关系（包含身份状态、链接原因、来源时间/版本）；保留材料版本、source locator、重复重数、账户映射范围。审核计划和回执绑定 source/material version、身份范围、book revision/input digest、choices/reasons 与 request ID；完成回执记录实际新增、修订、撤回、证据补充、重复、排除及 unresolved 数。候选已列 ID 和对象，不要求现在定 SQL，但关系和版本绑定需明确。

**证据。** `current-model-evidence.md` §2 的 `source_material_versions`、`source_observations/source_execution_links`、账户映射、撤回状态及 §3.3；`replay-import-evidence.md` §5 I09–I14、§6。

## P2 — 一秒目标缺少可复现的计时和通过门槛

**事实。** 候选稿第 20 行限定目标为数据齐备、服务已启动时首页/交易库完整首屏，并要求分测冷、热、重启首读及导入/修订后的首次打开。第 196、205 行区分保存成功与读模型就绪，明确不得把更新中或旧结果当成功。缺少的是计时起止、用户可见的“完整且可操作”定义、样本数/分位、代表数据规模、浏览器/硬件/缓存条件、并发，以及保存到新发布可用是否也受 1 秒预算约束。

**反例。** warm 后端查询在 1 秒内，但 HTTP、序列化、客户端解码和图表渲染后首屏数秒才可用；或 1 秒时先展示旧 summary，后台仍在计算，两个场景都不能算“完整正确首屏达标”。

**建议。** 冻结验收协议：分别给出导航/筛选到完整首屏可用的端到端时间，与事实保存到准确新 publication 可读的时间及各自预算；指定数据集规模与覆盖、浏览器/运行时、冷/热缓存定义、样本数及 p50/p95/失败条件、页面/筛选/分页路径和数据正确性断言。保存后的旧完整版本可展示时，必须标明旧版本并且不得计入新数据时延通过。

**证据。** `current-model-evidence.md` §5：真实源包/窄包 p50 约 8.47s/7.18s，首次准备约 7.31s，均未覆盖浏览器和完整财务；`measurement-06` 真实规模整次 FAIL，`measurement-07` 仅 synthetic 修复通过、真实规模 NOT VERIFIED。候选稿第 20、196、205、219 行。
