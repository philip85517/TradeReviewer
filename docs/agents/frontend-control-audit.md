# 前端控件与视觉空间审计规范

本规范用于 TradeReview 的首页及其他交互页面，记录一次可复现、可审查的控件普查、视觉空间诊断和修复复验。它是开发约束，由 agent 在适用时执行；不是运行时监控，也不表示已安装自动钩子。

## 1. 触发与范围

面向前端页面或控件的语义触发本规范，例如中文提到前端、控件、按钮、点击、交互测试、检查、验证、走查、验收，或视觉跳动、抖动、对齐、布局、无响应、空间诊断；英文示例包括 `UI/control audit`、`click/interaction test`、`visual regression`。单独出现“测试”或“检查”而没有前端页面/控件意图时不触发。按用户意图判断，不做机械关键词匹配。

影响前端页面的开发完成后、交付前自动执行，范围包括交互、layout、状态 wiring 和视觉回归；局部修复检查受影响控件及其上下游，整页改动或明确要求“所有控件/100%”时，按全量登记执行。只读审计本身不自动授权修复；设计请求本身也不自动实施代码。纯后端或纯文档任务按实际影响判断，确实没有适用 UI 时记录 `NOT APPLICABLE`。

本规范不替代 [开发工作流](development-workflow.md)、[任务拆解标准](task-decomposition.md)、[UI 任务与验收模板](ui-task-templates.md) 或 [本地任务跟踪](issue-tracker.md)。任务票仍须写明精确范围、负责人、证据和依赖；本规范提供检查方法与可复制记录。

## 2. 冻结可比条件

开始检查前冻结以下信息，并把它们写在报告顶部：

| 项目 | 必填内容 |
| --- | --- |
| 版本 | worktree、分支、基线/最终 commit 或变更标识；dirty 工作树必须有文件内容 manifest/hash，大小/mtime 只能辅助；记录生成时间 |
| 服务 | 启动命令、端口、最终 URL、进程/会话；浏览器新鲜打开时间 |
| 数据 | 数据集、过滤值、分页和动态数据边界；写入时的显式 `TRADEREVIEW_DB_PATH` 隔离库 |
| 页面状态 | 导航是否展开、阶段/选中/展开/空/加载/错误/候选状态、滚动位置 |
| CSS 环境 | CSS 视口宽×高、浏览器缩放、DPR、滚动容器与 `scrollTop/Left`；截图像素尺寸另列 |
| 排除 | 用户明确排除的范围、来源、适用版本和分母移除理由 |

原稿像素尺寸不等于 CSS 视口，不能据原稿截图像素直接推导断点。没有用户原稿时，按已经记录的 UI 要求和现有视觉规范验收，并标明依据。窄屏默认适用当前规格；本次授权的“窄屏不修复”只能记录为本次版本/范围的 `EXCLUDED`，不能变成全局默认。

最终构建、运行服务和浏览器证据必须对应同一最终内容 manifest/hash；不能用构建前的指纹或另一工作树的服务代替。若版本或环境变化，旧证据只作为历史记录，不能直接支持新结论。只读审计也要冻结状态，以免动态数据在普查中改变分母。

## 3. 控件全集与登记

先用 DOM、可访问性树（AX）和源码交叉登记，再操作。登记对象包括按钮、链接、表单提交、下拉/菜单/选项、展开/折叠、条件出现的弹窗与确认项、card、icon、SVG 热点、图表点、绘图工具、分页、滚动加载、键盘入口和由快捷键触发的动作。`disabled` 控件也登记，必须写禁用原因；禁用不等于无响应。

动态、分页和可选状态须公开固定边界：本轮数据集、页码、最大页、每数据点实例、每选项、每重复卡片是否单独登记。不能在用户要求 100% 时偷偷抽样。对隐藏或条件出现的控件，写明进入条件和如何退出；对弹窗写明打开、关闭、取消和背景/键盘路径。

每项使用稳定 `ID`，重复实例写稳定父 ID 加业务键或索引；不要只用文本、颜色或易变坐标。控件登记至少含以下字段：

| 字段 | 说明 |
| --- | --- |
| ID / 版本范围 | 稳定控件 ID、适用 commit/数据边界 |
| 定位 | DOM/AX/source 位置、重复规则、数据键/选项值 |
| 前置条件 | 导航、权限、选中对象、弹窗、分页、焦点 |
| action / 输入方式 | 鼠标、键盘、模拟触控或物理触控，明确按键/坐标/对象 |
| expected / state contract | 预期本地、父级、全局、API、URL 和可见结果 |
| visual target | 影响的布局、容器、轴、页下游和视口 |
| evidence / status / owner | 证据路径、`PASS`/`FAIL`/`NOT VERIFIED`/`NOT APPLICABLE`、负责人 |

登记全集与实际执行项分开保存。排除项保留原始全集中的记录，标记 `EXCLUDED` 作为范围字段，不把它当作状态或 `PASS`；同时解释为何从本轮分母移除。

## 4. 覆盖率与状态口径

覆盖率只回答“登记项是否真实执行且有结果证据”，通过率另算：

```text
执行覆盖率 = 有真实操作且有结果证据的已执行登记项
           / 本范围应执行的登记项
点击覆盖率 = 有真实点击/按键且有结果证据的登记项
           / 本范围应点击/按键的登记项
点击尝试率 = 已真实尝试点击/按键的登记项 / 本范围应点击/按键的登记项
状态/选项覆盖率 = 有真实状态/选项操作且有结果证据的登记项
                 / 本范围应验证的状态/选项登记项
结果通过率 = PASS 登记项 / 已执行且有结果证据的登记项
```

`FAIL` 是实际测过并观察到不符合预期，可计入相应覆盖分子；`NOT VERIFIED` 不可计入覆盖；缺失证据、无法操作或只读源码分析不能算已覆盖。仅有尝试没有结果证据只能计入尝试率，不能计入点击覆盖。若某范围没有应执行项，填写 `NOT APPLICABLE` 并说明分母为空，不写成 100%。点击覆盖、状态/选项覆盖、尝试率和通过率分别报告，禁止用一个百分比替代其他指标。不同版本、不同数据集、不同登记边界的不同轮次数字不能混用。

## 5. 真实操作与证据

优先使用 computer use 完成真实鼠标和键盘操作。首次使用工具先读初始化文档，再取得新鲜快照；每个关键步骤记录操作前、操作中、操作后状态，并记录返回、关闭、刷新后的结果。DOM 几何只读检查可辅助定位，但不得用合成事件、强制调用 handler、mock state、直接 API 成功或 HTTP 200 替代真实 UI 操作。

操作序列至少包含：

1. 读取真实页面和目标控件，确认对象身份与前置条件。
2. 真实鼠标点击；适用时用键盘 Tab、Enter、Space、箭头、Escape 和提交快捷键复验。
3. 对展开、弹窗、图表点、分页和条件项记录中间状态、可见反馈及布局变化。
4. 关闭/返回导航，再刷新或重新打开，确认契约规定的状态是否保留。
5. 工具超时先读取真实浏览器状态、控制台和网络，再决定是否无响应；不能因工具超时自动判定应用无响应。

单独列出工具能力未验证的项目。鼠标、键盘、模拟触控、物理触控和组件合成事件证据分列，不能互相冒充；没有物理触屏证据就保留 `NOT VERIFIED` 或按明确范围写 `NOT APPLICABLE`。

无响应诊断先写该动作期望出现的可见反馈、规格规定的等待条件和超时预算，再逐层定位：真实 `enabled/disabled` 与禁用原因、前端事件是否触发、本地状态与父级/全局状态是否更新、API 请求与返回（若契约有请求）、最终渲染结果。`pending/loading/error/cancel` 应能在 UI 或明确日志证据中观察；外部请求/工具失败要与应用事件未接线区分，不能凭“有网络请求”或“没有网络请求”下结论。契约没有异步行为时不虚构请求或等待阶段。

## 6. 缺陷分类与空间测量

缺陷至少分为：意外视觉位移、布局/密度/对齐/截断/遮挡、无反馈或错误状态、点选身份错误。另标记来源为“设计待补”或“实现故障”：设计待补需引用对应状态稿/现有 UI 要求及空间预算、信息顺序、对齐、命中区域和交互反馈；实现故障需给出当前实现与已批准契约的差异。若已有设计未覆盖该状态或布局需要调整，问题票必须列出需补的状态稿或可审查 HTML 原型、比较 viewport、信息顺序、空间预算、对齐、命中区域和反馈，并在已授权范围准备方案；必需设计证据未补齐时，不能由实现者自签视觉 `PASS`。无用户原稿但已记录完整需求时，可按既有规范验收，不自动阻塞，也不重复审批已经授权的方案。预期导航、展开或滚动会造成的变化，必须与异常跳动分开记录。

动作时序测量在同环境、同起始状态下观察目标动作的 before/during/after；during 和 after 可以是动作导致的不同目标态，须记录状态变化。视觉同态对照则在批准参考或旧版基线的对应状态、相同或已说明的视口/数据条件下比较，不能把动作前后两帧称为同态对照。两类测量均记录控件和父容器 `getBoundingClientRect()` 的 `x/y/width/height`、document 坐标、viewport 坐标、滚动偏移、舞台/图表容器高度，以及价格轴、侧栏、表单和页下游的 Y 位置。

真实动效正常轨迹必须保留并观察中间帧；禁用动画只可作为辅助定位，不能替代正常动效证据。CLS 只能辅助，不能替代几何和截图证据。

| 对照 | 必测观察 |
| --- | --- |
| before / during / after | 控件、父容器、舞台、页下游的位置和尺寸变化 |
| data / selected / expanded | 首屏层级、间距、候选区、按钮和主要信息是否跳动 |
| empty / loading / error | 空槽、错误反馈、重试/取消、虚假零线和内容回流 |
| breakpoint 两侧 | 关键断点前后列数、对齐、遮挡、滚动和核心动作可达性 |

保留批准设计的尺寸和视觉预算。特定稳定容器可在其规格中约定例如 `<=2 CSS px` 的变化，但这不是所有操作、所有页面的全局标准。不得靠缩小全页字号或命中区、隐藏主要信息、固定虚假零线抹平缺陷；若用户排除某断点，记录 `EXCLUDED` 和原因，不能写成 `PASS`。

关键断点必须在两侧各取至少一个可比视口；检查列数、间距、主图/侧栏占用、主要信息首屏可见性、滚动边界和核心动作可达性。长中文、长数值、候选重合和空态是独立场景，不能用普通短文本的几何结果替代。软件键盘造成的 CSS 视口变化与桌面窄屏分开记录；没有真机键盘证据时不声称通过。

视觉预算表应把“允许变化”和“禁止变化”分开：

| 区域 | 批准尺寸/预算来源 | 允许变化 | 禁止变化 | 证据 |
| --- | --- | --- | --- | --- |
| 主图/舞台 | `<规格或现有契约>` | `<动作导致的预期变化>` | `<意外位移/虚假零线>` | `<截图+rect>` |
| 侧栏/候选区 | `<规格或现有契约>` | `<内部滚动/展开>` | `<撑大主图/遮挡>` | `<截图+rect>` |
| 顶栏/底栏/页下游 | `<规格或现有契约>` | `<明确导航反馈>` | `<无故推移核心动作>` | `<截图+坐标>` |

## 7. 状态契约与真实作用域

每个动作写一行状态契约，至少覆盖前态、动作、本地/父级/全局/API 变化、可见反馈、布局/viewport、持久化/返回/刷新及失败/取消：

| 前态 | action | 本地/父/全局/API | 可见反馈与布局 | 保存/返回/刷新 | 失败/取消 |
| --- | --- | --- | --- | --- | --- |
| `<状态>` | `<真实操作及输入方式>` | `<准确对象、请求、游标、URL>` | `<文字/图表/尺寸/视野>` | `<应保留或清除>` | `<旧值、提示、重试>` |

确认操作作用域是真实的：实体搜索不等于页面过滤，必须实际达到 0 条记录或 0 个图点才可声称清空；清附加筛选、清主范围和恢复默认是不同语义。`null`、`undefined`、空字符串和缺失字段不能混同。币种、期间和对象 ID 必须完整；切换对象后验证完整身份键仍合法，失效或移除对象不能泄漏旧详情。若契约允许保留同域日期层级或其他状态，按契约保留，不做无依据的全局清空。无响应时沿用本节的 enabled→事件→状态→请求→渲染诊断；无异步契约时只验证同步反馈。

图表点选记录屏幕距离、密集点歧义和候选决策，当前规格中的 22px 半径、220/320 等数值只在明确规格范围内有效，不得升级为全局默认。按契约区分 hover/focus 预览与 click/Enter commit；前端 network、console 和无网络现象只补充定位，不能仅凭无网络推断无响应。

状态契约还要写明动作应出现的反馈、可接受等待条件和超时预算，并分别记录 enabled、事件、状态更新、请求/返回、渲染和 cancel 的观察结果；没有异步行为的动作标明“无请求阶段”，不为它虚构 loading。

## 8. 诊断与修复方案

修复前先建立可复现步骤、版本/数据边界、状态空间和根因假设，不先盲改 CSS。逐项评估 `normal`、`selected`、`expanded`、`empty`、`loading`、`error`、`ambiguous` 和 `longtext` 的适用性，并检查范围内适用的状态；某状态不存在或明确不适用时写出原因，不强迫纯按钮虚构八种状态。对适用状态记录尺寸预算、允许回流和最小可见信息。

修复方案必须关联：已批准的规格/图稿、负责的 element ID、owner、用户旅程和 evidence 路径；说明作用域、预期布局变化、状态链变化、失败/取消行为及不变项。修复后真实验证相关反例，并由未实现该 UI 的审查者做独立视觉对照；再检查跨组件和上下游回归。

先修正根因，再做局部稳定化。例如状态高度不一致，应优先补齐状态契约或稳定容器，而不是用全页缩放、隐藏信息、扩大不可见命中区或强行固定一个错误高度。若采用局部滚动、最小槽位或候选压缩，记录它对阅读顺序、键盘焦点、屏幕阅读器和返回行为的影响。

修复审查至少复跑：原问题步骤、同控件的取消/返回路径、最相邻的上下游控件、对应空/错误/长文本/歧义反例，以及适用范围内关键断点的两侧。若用户排除某断点，保留排除来源和范围，不能以未检查写成通过。跨组件事件要追到最终可观察动作，不能只证明 callback 被调用。

## 9. 数据、测试与放行门槛

保护原业务数据。`conf/runtime.json` 的绝对共享业务数据库和端口保持不变；写入型浏览器验收必须显式设置 `TRADEREVIEW_DB_PATH` 使用隔离库。SQLite 备份使用一致性 backup，不能直接 `cp` 正在写入的数据库而遗漏 WAL/SHM。验收前后记录逻辑 counts、关键内容摘要或 hash；不要用 SQLite 文件字节 hash 冒称业务数据未变。

所有核心 write flow 都要真实保存、返回、重新读取和 reload；回调成功、注入 props、mock 保存或重新渲染 fixture 不算闭环。保存失败、取消和版本冲突须验证原输入/派生字段的保留或明确重载，并确认再次编辑可保存。

功能正确性、端到端状态链和独立视觉是三道独立门槛。保存基线 commit/内容指纹和最终变更标识，在相同命令、配置、数据和工具版本环境下对照；基线与修复版本不要求相同。仅证明某文件未改不足以归因，无法确认的原因保留 `NOT VERIFIED`。全仓检查与定向检查分别报告；测试 `FAIL` 必须保留。独立审查者不能是所审 UI 的实现者。

UI 交付仍须在真实浏览器新鲜检查，提供可点击 preview URL、服务仍运行的证据和启动命令；纯文档交付不要求 UI、数据库或 preview 验收，但应做链接/结构/差异检查。

范围内修复若有 `FAIL` 或必需门槛 `NOT VERIFIED`，阻止声称修复完成；审计任务可以输出缺陷并完成审计报告，但不能据此声称产品修复完成。全仓必需检查失败阻止整体放行；局部修复 `PASS` 不等于全仓 `PASS`。放行前按下面顺序核对，任何适用的 `FAIL` 或 `NOT VERIFIED` 都要保留并指派后续责任人：

1. 范围、版本、服务、数据、视口、过滤状态和排除记录完整。
2. 控件全集可回溯到 DOM/AX/source，动态边界和分母已公开。
3. 每个执行项有真实输入、实际结果和证据；覆盖率与通过率独立计算。
4. 空间测量覆盖 before/during/after、相同状态对照和关键断点两侧。
5. 状态链覆盖准确身份、作用域、返回、刷新、失败和取消。
6. 修复后的反例、上下游和独立视觉对照已复验。
7. 写入流使用隔离库并保护原始业务数据；纯文档任务说明适用门槛为 N/A。

## 10. 可复制登记与验证表

```markdown
### 控件登记
```

## 11. 证据边界与历史案例

一条证据只能支持它真实覆盖的状态、输入方式、数据集和版本。例如一批真实鼠标点选不能自动证明键盘、hover、触控、所有过滤组合或另一版本的数据点；单元测试不能自动证明真实图表视野；截图不能自动证明保存后 reload。报告中明确“证明了什么”和“没有证明什么”。

历史修复中的屏幕距离半径、舞台高度、断点、候选数量、点击总数或某次窄屏排除，均是该版本视觉契约和数据边界的来源案例。除非当前任务再次引用批准规格，否则不能把这些值或结果当作全局默认、全站阈值或全部控件通过。

若同一控件在多个状态有多个实例，证据要能由 ID、业务键、索引和状态重建。若一次操作同时改变多个容器，记录父级和页下游的变化，不能只量被点击元素。若动画或异步绘图可能延迟提交，保留时序和中间状态，不能以同步 mock 消除竞态。

## 12. 回归记录与触发说明

已有失效证据必须保留；回归时重新打开受影响 issue，并同步更新 feature README、`DESIGN-COVERAGE.md` 和 `FINAL-ACCEPTANCE`（若该 feature 使用这些记录）。不能以新截图覆盖旧失败，也不能用一次局部通过抹去整页未验证项。

本规范路径固定为 `docs/agents/frontend-control-audit.md`，供项目入口、任务模板和开发后交付提示引用。入口应按语义触发相关检查，不应声称存在后台监听器或已安装钩子。每次适用执行都应把本规范、版本、范围、实际动作和证据链接到任务记录中；本规范本身不会扩大用户已授权的修改范围。
