# 策略台视觉设计方案 V1.0

策略台帮助研究者把投资想法整理成可复用的方法，在明确的历史条件下运行，再用成交证据和结果检验它。本方案围绕“策略库 → 创建实验 → 观察与回看 → 结果和比较”展开：策略保存方法，实验保存一次研究的版本、条件和进度。

核心视觉主张是：**先确认正在看的策略、组合和日期，再看图表发生了什么，最后用相邻的解释区回答为什么。** 页面优先保证身份清楚、时间可信、原因可查，接受必要的纵向滚动，保留完整观察信息。

第一章说明全局选择，第二至第十一章依次解释各项任务的画面与取舍，第十二章集中说明公共控件，第十三章串起完整旅程，第十四章给出评审重点和依据。各章先讲设计理由，再给图示，精确规则、参数与引用放在可展开区域，便于连续阅读和按需核对。

## 一、这次设计保留什么、改变什么 {#chapter-ST01}
这次设计保留策略与实验分离、四步创建、逐日观察及完整原因解释，调整的是这些内容的视觉层级与呈现方式。方案采用当前V2.5公共控件，把身份、日期、图表和解释组织成稳定的阅读顺序；需要更多空间时允许向下滚动，优先保证信息完整和可读。

### 先分清可复用的方法与一次研究

策略库保存“用什么办法选股、何时买入、何时退出”，我的实验保存“用哪个版本、从哪天开始、投入多少资金、运行到哪天”。分开保存需要创建时明确选择版本，但修改今天的策略不会改写昨天的实验。创建始终从“我的实验”开始；途中缺少合适策略时可以就地组装，保存后回到原来的选择步骤。

回放观察、阶段结果和组合对比共用实验身份与时间说明，查看结果和追查事件可以连续往返。策略台里的用户是观察者，买卖由策略和执行规则决定，候选名单只表达研究证据与策略意图。

### 三个视觉选择及其代价

**图表与解释相邻。** 主图呈现走势和成交，右侧说明持仓与调仓原因，方便逐项对照。常驻解释会占用图表宽度，因此低频配置另开覆盖层；窄窗口改为先图表、后解释的纵向顺序。

**共用控件语言，按研究任务组织页面。** 颜色、字号、按钮、输入、焦点和金额展示沿用V2.5，策略身份、日期与回放工具则遵循本模块的业务顺序。首页的72px导航、64px页头和八行持仓表只属于首页布局，不能直接成为策略台的空间预算。

**保留完整信息，允许向下滚动。** 延续0.7已确认的完整观察与页外滚动。四项指标合成88px连续摘要带，减少卡片嵌套；比旧紧凑摘要略高，换来统一字号与可读金额。图表净绘图区仍至少320px，尺寸细则和来源性质列在下方。

## 二、策略库：先找到方法，再看规则 {#chapter-ST02}
策略库首先帮助用户找到可复用的方法，并判断它是否值得进一步查看。因此完整策略放在默认视图，标的筛选、买入信号和止盈止损三类包作为相邻目录。库内的主动作是“新建策略”，保存后进入策略详情；实验仍从“我的实验”发起，两个入口各自承担清楚的任务。

列表先呈现名称、版本、规则摘要与状态，搜索、筛选和排序固定在顶部。本版建议用紧凑行替代大卡片，让更多策略能同屏比较。代价是读规则全文需要进入详情，所以摘要必须足以帮助判断，返回时还要恢复查询和位置。这项密度调整属于本次建议，历史“整体模型认可”没有批准这些新尺寸。

包目录复用查询工具，额外显示使用策略数和版本发布时间，帮助判断依赖关系与新旧程度。“查看详情”只阅读说明，回到选择列表后再点“使用此包”；多一次明确选择，避免浏览说明时意外修改配置。下图展示默认目录、查询工具与紧凑行如何配合，管理规则在图后逐项列出。

## 三、组装策略：三个包，一份可追溯的版本 {#chapter-ST03}
组装策略的目标，是把三个职责明确的包保存成一份可执行、可追溯的方法。页面按“筛选 → 买入 → 止盈止损”排列，先交代包名、版本与命名预设，再展示关键规则和数据要求。排序、仓位分配与再平衡仍属于完整策略配置，第三个包不能替代这些职责。

理解包的说明与观察当日证据需要不同空间。包详情使用较宽的覆盖层，运行检查区只保留当日信息；这会增加一次打开说明的动作，却能避免长配置常驻挤压图表。关闭详情恢复原位置，未保存内容不丢失；用户无需逐条搭建原子条件或上传脚本。两类区域的宽度在规则中明确。

版本操作同样需要付出一次明确选择：“保存新版本”延续同一个策略，“创建副本”生成独立策略。已有实验始终锁定完整策略及三个包的原版本，这样库内调整不会改变历史结果。

## 四、我的实验：每条记录都有下一步 {#chapter-ST04}
我的实验帮助用户找回研究进度，并判断接下来能做什么。每条记录把状态、日期区间、策略组合与下一步动作放在同一上下文中，让用户从上次停下的位置继续。

状态靠近实验名称，操作入口位置固定、文字随状态变化：草稿对应“继续编辑”，未开始对应“进入实验”，暂停对应“继续观察”，完成对应“查看结果”，失败对应“查看原因”。统一位置便于扫描，具体文案则说明这次点击的结果；代价是用户需要读清状态，不能把所有入口都理解为“继续运行”。

重新打开已运行的实验先保持暂停，需要用户主动推进后才继续揭示行情。这多一次操作，却避免刚进入页面就看见新的历史。搜索、筛选和排序沿用库的操作方式，各自保存条件；两页之间切换不会创建草稿或自动选中策略。下图用五种状态展示同一行布局如何提供不同的下一步。

## 五、创建实验：四步把假设说明白 {#chapter-ST05}
创建实验把研究假设变成一份可以复查的运行条件。四步依次回答“研究哪段历史、采用什么方法、预期怎样配置、是否按这些条件开始”：先固定起点，再选择完整策略，随后预览组合，最后确认版本、资金、费用与执行假设。分步增加了确认成本，但能在产生运行前发现条件不一致，确认后进入尚未开始的工作台。

选择策略支持一个或多个完整策略，每个组合使用自己的本金。缺少合适方法时，可以就地组装；保存成功只追加新版本，取消则原样返回，原有选择和查询都保留。

预览用历史可知数据形成候选和目标仓位，并把“目标”与“实际”分列。目标表达策略希望如何配置；尚未运行时实际持仓仍为0、现金仍为100%。这会让页面多一层信息，却能避免把计划误读成成交。没有候选也可能是有效结果，应说明原因并保留现金状态。

## 六、观察工作台：围绕同一天理解一个组合 {#chapter-ST06}
观察工作台以“同一个组合、同一个查看日”为证据范围，让用户能够把走势、成交和原因相互核对。先看实验名与组合版本，再看摘要和日期，随后阅读主图，最后在相邻检查区查看解释。身份和时间先明确，数值与原因才有共同的含义。

净值曲线呈现组合变化，切到标的K线后，成交标记说明具体买卖位置。右侧“组合详情”在概览、调仓记录和统计指标之间切换，始终属于当前组合与查看日。解释常驻会缩窄主图，但减少了反复打开说明的成本；因此长原因自然换行，低频配置移入覆盖层，页面允许纵向延续。

净资产、累计收益、最大回撤和仓位组成摘要，分别帮助判断表现与风险。播放/暂停、下一交易日、速度和回看动作放在主图下方固定位置，避免日期文案变长时动作跑位。组合选择区固定宽度，保留当前项和“更多组合”，增加组合数量不会向下挤压主图；名称可换行或在列表完整阅读。

切换组合只改变观察对象，查看日保持不变。执行落后的组合显示自己的真实已完成日，提醒用户这些数据的有效范围。完整画板展示上述阅读顺序，随后局部详图用于核对日期与摘要的层级。

## 七、推进与回看：看到新一天，仍知道自己看过什么 {#chapter-ST07}
推进、回看和已经看过的历史是三件不同的事。推进揭示新的行情与执行证据，回看只改变当前查看位置，而“已看后续”保留已经获知的信息。把三者区分开，用户才能复查早期判断，同时知道这次复查已经受到哪些后续信息影响。

点击“下一交易日”后，日期、行情和当日证据一起更新，新一天必须出现在主图中。有成交才出现成交标记与实际持仓变化；没有成交就只揭示行情。连续播放按交易日依次揭示，速度只调整观看节奏。展开到指定日期前说明将揭示的区间，失败时停在最后完整成功的一天，保留图表与原因。

例如已看到6月28日，再回到6月14日，图与当日持仓回到起点，但“已看后续至6月28日”仍然保留。这里接受了不能恢复首次盲看状态的限制，换取真实的研究记录。“返回最新”只回到已展开的截止，不产生新进度。

## 八、阶段结果：先解释表现，再回到发生的那天 {#chapter-ST08}
阶段结果把一段运行组织为表现、风险和事件原因，帮助用户判断结果如何形成。所有内容先限定统计到哪一天，再展示净值、回撤、仓位、已实现与未实现盈亏、费用、换手和贡献，避免把不同期间的数值当成同一结论。

净值、回撤和仓位共用图表区域，切换视角不重新运行实验。共用区域节省空间，但不能同时对照三个图；稳定的区间和截止提示使切换前后的含义保持一致。贡献解释收益从哪里来，调仓表则帮助追查策略做过什么。

点击事件进入发生当日的观察画面，主图、持仓和原因一起切换；关闭事件详情只关闭说明层，日期仍留在事件日。“返回阶段结果”才恢复原区间、筛选和滚动位置。两个返回动作需要分别辨认，却能同时保留事件调查和结果阅读的上下文。下图展示总览、贡献与事件入口的层级，精确计算口径列在图后。

## 十、等待与异常：说明发生了什么，给出下一步 {#chapter-ST10}
等待与异常状态要让用户知道哪些信息仍有效、哪部分尚未完成，以及可以怎样继续。提示靠近受影响区域：列表失败保留查询，包不兼容标到对应槽位，执行失败放在日期和回放附近。局部提示需要用户关注具体区域，但能避免一个全局错误掩盖仍然可用的内容。

首次加载使用骨架并保留区域尺寸；更新已有结果时，保留旧内容并标明“正在更新”，只有新的有效请求完成后才替换。保留旧内容可以持续阅读，也带来误认最新数据的风险，因此对象身份与有效日期必须清楚。快速切换组合时，较早请求不能覆盖后一次选择。

空库、没有匹配、没有候选和执行失败分别说明。合法的无信号结果仍可保留现金组合，未知数据不能填成0。正常状态只呈现结果与当前范围，无需常驻绿色“数据完整”徽章。下图展示不同问题的位置和恢复入口，逐项保留内容在规则表中核对。

## 十一、窗口变窄、内容变长时，任务顺序保持一致 {#chapter-ST11}

## 十二、公共控件怎样进入策略台 {#chapter-ST12}
公共控件让策略台延续全站熟悉的文字、颜色与操作反馈，降低从首页进入后的学习成本。复用时同时明确业务作用域：列表筛选只改变所属列表，图表标签只切换视图，回放动作才揭示新一天。外观一致有助于识别操作，但不能据此把不同状态混成同一个动作。

蓝色用于主动作与选中，绿色和红色用于盈亏，黄色用于需要注意的限制。版本、截止和普通说明保持中性。颜色只承担约定的含义，同时配合文字、形状与可见焦点，让用户能辨认当前对象、操作反馈和不可用原因。

统一尺寸能保持跨页面的密度与操作习惯；长名称和窄窗口则通过换行、布局重排及扩大命中区处理，接受额外的空间占用。业务空态由容器说明，按钮只呈现适用的控件状态。下图展示共享视觉语言，展开区按映射、状态与反馈、回放行为、参数和来源分组，避免参数抢占设计论述。

## 十三、走完一条完整路径，返回后仍找得到原来的位置 {#chapter-ST13}
完整旅程是否连续，是这套方案能否成立的整体判据。用户从草稿进入组装、查看包说明，再回到原选择继续，最后在结果和事件之间往返时，应始终找得到原对象、版本、日期和来源。单个页面正确不足以保证这一点，返回与刷新后的状态同样属于设计。

以继续实验草稿为例：第二步新建策略，查看筛选包说明后返回保存，新策略追加到原选择，其他已选策略仍然保留。继续确认后进入T0，推进至首次交易，再从结果进入事件日查看原因，最后返回原结果位置。这条路径把创建、观察与解释连接起来。

保留这些上下文需要分别保存草稿、运行进度和各视图的位置，增加了状态管理成本，却避免用户反复重建查询、丢失选择或误认已看历史。关闭详情留在事件日、显式返回恢复结果，是这项选择的具体体现。下表列出每次往返应保留什么，末尾再规定后续实施的验证顺序。

<details>
<summary>查看跨页面状态与后续实现接受顺序</summary>

| 路径/元素 | 需保存的上下文 | 返回或重开 |
| --- | --- | --- |
| FLOW01 库→策略→包 | 库类型、查询、排序、页码、滚动、焦点、详情版本 | 逐层返回；只读不修改 |
| FLOW02 实验草稿→组装 | 草稿身份、步骤、各输入、已选版本、原查询 | 保存追加；取消不变；失败留组装 |
| FLOW03 确认→运行 | 配置与版本快照、资金、执行约定、数据版本、幂等提交身份 | 一次运行；成功后未开始；失败无半成品 |
| FLOW04 观察→配置→包 | 组合、图模式、日期、视野、展开的检查区 | 返回同对象同日、暂停 |
| FLOW05 结果→事件→返回 | 结果截止、过滤、区间、滚动、焦点；观察投影分开存 | 关闭详情留事件日；显式返回恢复结果 |
| FLOW06 比较→观察→返回 | 所选组、共同区间、图模式、表格位置 | 不把观察日期覆盖比较截止 |
| FLOW07 派生 | 来源策略/实验版本与已看记录、新草稿身份 | 原运行不改；新草稿可编辑 |
| FLOW08 保存→列表→刷新 | 草稿/版本/运行进度/成交估值/已看来源真实持久化 | 读取同身份同值；失败不伪报成功 |

实现先接受“确认T0→下一交易日→真实图表新bar/适用成交→回看→返回最新”的最小闭环，再扩展结果与比较。之后在隔离数据库验证保存→返回列表→重新打开→刷新→账本对账；功能正确性、时间安全、视觉对照分别验收。设计图不替代这些运行证据。

</details>

## 十四、依据、取舍与评审重点 {#chapter-ST14}
本次评审集中判断三项新增视觉选择是否支持研究任务。紧凑列表换来更多同屏策略，但规则全文需要进入详情；88px连续摘要换来统一字号与可读金额，但占用更多高度；较宽的包说明层与常驻观察栏分工，使长配置和当日证据各有位置，但查看配置需要打开一层。评审应看这些收益是否足以承担对应成本。

具体可以核对：只看列表能否辨认方法与版本，摘要和日期是否清楚且主图仍可读，查看包说明后能否理解它与当日原因的区别。策略与实验对象、四步路径、版本不可变、计划与成交分离，以及已确认的完整观察方向，继续作为本方案的前提；新尺寸与视觉分配仍待用户评审。

依据分两类使用：历史规格、融合契约和后续用户确认决定业务及布局边界，当前全站V2.5决定公共控件语言。后续完整观察与外层滚动决定优先于较早的严格单屏预算；历史样式只帮助理解原意。原型中未验证的持久化与未来信息安全，仍需后续实施验收。

评审意见可以落到可观察问题，例如“这里看不出当前日期”“原因区太窄”“返回后希望仍停在这条事件”。方案通过后再按覆盖矩阵分解实施。本次未修改生产页面、原始交易数据，也未提交远端；来源、变更归属及交付边界在下方集中列出。
