# 一秒优化：实验路线说明

**先验证，再决定是否开发。** 目前最值得试的是：在交易或其他相关数据变化时，针对受影响的部分准备可复用的结果并保存；打开首页或交易库时，读取完整范围的摘要和当前页，详情及来源按需读取。它是优先实验假设，尚不是最终选定的架构，也没有性能保证。

## 为什么优先试这个方向

现有隔离样本的一次响应约 34.33 MB；服务端会循环整理数据并计算校验摘要，浏览器还要校验和处理。仅将展示列表分页，未必减少服务端整理和计算。因此，实验需要同时考察**少做重复计算、少传与页面无关的数据、保持结果正确**。[诊断依据](../home-trades-recovery-diagnosis-2026-10-28/PROTOCOL-REVIEW.md)；[独立审查](../../docs/backend-design/page-reading-architecture-review-2026-10-29.md)。

|路线|可能的收益|主要疑问|本轮作用|
|---|---|---|---|
|维持现有全量来源读取|无需迁移|大响应与重复处理已经出现|现状基线|
|只缩小接口和做服务端分页|减少部分传输|若底层仍全量整理，首读不一定变快|对照或诊断，不能单独认定达标|
|数据变化时准备可复用结果，页面窄读取|可能同时减少重复计算和传输|导入或修订后要更新结果；行情、汇率和复盘的变化需要各自处理|**优先实验**|
|所有筛选和日期组合都提前计算|读取可能快|组合过多，更新与存储成本难控制|暂不作为首选；按实验再评估|

这里的“提前准备”并不意味着只处理新增的一条成交。例如，补录去年某笔买入，可能影响之后同账户同标的的回合与成本，必须重算受影响的后续结果。交易、行情、汇率和复盘不同步更新，也不能一律使用同一个更新时间。

## 怎样判断是否值得继续

1. 用隔离副本建立当前首页和交易库的时间、响应量和数据规模基线；保留运行环境及原始证据。
2. 制作一次性的最小实验，测首次准备、没有变更时的重复读取、变更后的更新、重启后读取、传输大小和资源消耗；与相同条件下的现状比较。
3. 对照页面数据和业务规则，检查范围、日期、跨页、历史补录、缺失依据、版本变化和失败恢复。不能只让数字看起来合理。
4. 在能够合法覆盖的范围内，分别测试首页和交易库的真实桌面完整首屏。冷／热、服务重启首读、导入或修订后首读各自按既定 1 秒门槛记录；写入与结果准备耗时以及完整等待另列。
5. 把通过、失败与未验证一起交给用户，达标且正确后再决定最终架构、切换和正式开发。若暂不能验证完整首屏，不能把局部实验说成已达到目标。
