**结论：现有全量计算入口可以供两类任务调用，但不能原样作为安全的局部重算接口。** 当前接口先校验全库来源，再计算所选范围；只缓存某个账户的行级结果不足以保证该账户汇总资格仍正确。下一步须验证“全库校验凭据＋分组事实/结果＋页面组合”的模块边界，之后才能接单笔及旧库批量后台任务。

## 依据与取舍

1. 真实内存SQLite与公开写入/计算入口证明：买100再卖40余60，公开修订卖出为20后余80；分次与批量相同事实的确定性业务字段一致。不是只比较数量，也未另写财务公式。
2. 最小反例证明：B账户月结来源缺少必要审计后，A行仍60股/市值720/未实现120，但A的合计不可用并保留全局缺口原因。不能向现有全库校验入口提交选中切片，不能直接沿用先前可用的合计。这里只保留现有规则，不裁定规则的业务合理性。
3. 分组候选身份需要账户、标的、性质及模拟运行；账户级费用、来源、行情、日历、FX、复盘、元数据和时点均是可能跨组的依赖。没有证明无关的依赖继续保守失效。局部接口尚未实现，不能据此宣称可用。
4. 原件与旧库分线测试：六CSV实际解析130成交；四份辅助对应82条旧事实，其他对应未证明则保留未知。首次导入用未含该文件的隔离库；旧库刷新消费保留人工修正的一致性备份，不重新OCR覆盖事实。
