# 数据库建模综合审查：先守住事实，再划清展示资格

**现有模型可以继续演进，当前不需要更换数据库。优先问题是：同一条事实的身份、保存前提和输入规则没有覆盖所有入口；首页又将部分证据缺口扩大为全局不可用。** 新增账户表或证据表可能有价值，但不能单靠增表解决这些问题。

本轮由三个 **GPT 6.1 Sol Ultra** Agent 分别审查数据库结构、网页业务链路、公开实践，协调者独立核验源码、重建结构，并用虚构记录调用真实存储代码复现四项问题。**报告审查通过不表示产品问题已经修复。** 未连接在线业务库，财务 P1/F07 与 Bars 继续暂停。

**需要保留既有基础，同时补齐业务边界。** 下表给出本轮可支持的判断；优先级表示后续处理顺序，不代表本轮已授权实施。

## 2. 从用户问题拆出问题树

**“交易库有记录、首页却没有展示”涉及四组不同问题，不能归为同一个数据库故障。** 写入正确、读取完整、计算资格充分、最终页面可用，应分别证明。

```text
页面能否可信地呈现交易、持仓与财务？
├─ A. 保存的成交事实是否可信？
│  ├─ DB01 不同账户的相同成交可能被去成一笔〔已复现〕
│  ├─ DB02 迟到的导入可覆盖后来已审计的修订〔已复现〕
│  ├─ DB03 改证券身份可重解释原有成交〔已复现〕
│  └─ DB04 非法数量、价格、费用或时间可以保存〔已复现〕
├─ B. 读出的材料是否足以支持当前选集？
│  ├─ DB05 局部证据缺口进入全局未知，影响范围不能缩小〔静态确认〕
│  └─ DB06 历史覆盖与历史汇率提供者未接通〔代码确认，任务暂停〕
├─ C. 事实修订后，历史判断能否追查？
│  ├─ 回合身份变化后，旧复盘如何关联〔待业务决策〕
│  └─ 最新行情缓存与固定版本复现如何区分〔适用边界〕
└─ D. 正确结果能否及时、清楚地发布？
   ├─ DB07 全量事实及多证券行情采集的实际成本〔待测量〕
   └─ 实际桌面页面、交互和重载后的结果〔本轮未验收〕
```

首页读取事务、计数及摘要绑定已经存在。它们有助于证明**这次响应与枚举的内容一致**，不能证明账户全部历史齐全，也不能独自证明首页具备计算资格。详细链路见[现状说明第4节](current-model.md)。

## 3. 四项已经复现的写入问题

**这里的“已复现”仅指受控调用真实存储代码得到预期反例。** HTTP 路由到 Store 的可达性另由源码核实；本轮没有发送 HTTP 写请求，没有复现正常界面的用户事故，没有判断业务库已有多少错误记录。

四个反例及执行结果分别见[测试源码](../../../.scratch/database-model-review-2026-10-26/evidence/store-probes.test.ts)与[4/4结果](../../../.scratch/database-model-review-2026-10-26/evidence/store-probes.json)。测试通过表示问题被复现，绝非修复验收通过。

### DB01 · P1：去重遗漏账户边界，可能少保存一笔成交

**两个不同实盘账户，即使在同一时刻以相同价格成交，也应先视为两条事实。** 当前普通秒级成交去重并非始终包含账户；月结、仅日期精度和模拟运行另有保护，不能泛化为所有导入都错误。

- **证据：** 合成账户 A、B，成交 ID、来源文件指纹不同，证券、秒级时间、数量、价格和费用相同，明确标记实盘。先后保存后，第二次报告重复1笔，最终只剩1笔。
- **定位：** `execution-reconciliation.ts:82–88,373–382,456–467`；Store `mergeExecutionsInTransaction`。详见独立报告 S04。
- **解释边界：** 同一账户的来源别名有时应合并，但不同账户不能未经映射就推断为别名；本反例没有证明历史数据已经误合并。
- **建议合同：** 先确定稳定账户身份和已确认别名；成交判等必须保留这个边界，再比较来源与重数。
- **后续验收：** 不同账户保留两笔；同账户跨来源能正确识别重复；同一来源的两笔真实同秒成交不被误删；明确账户纠正仍有效。

### DB02 · P1：过期导入可覆盖后来已审计的修订

**事务能保证一次保存整体完成，却不能识别请求是否基于旧数据。** 专用修订入口有前后记录比较；普通导入的显式替换没有同等前提。

- **证据：** 原价123.45，先通过修订改为130并留下审计；再提交旧预览的显式替换，当前价格变回123.45，审计仍保留。
- **定位：** `sqlite-store.ts:1260–1286` 的合并与替换，对照 `:1294–1364` 的修订检查。正常导入确认调用此合并入口；详见 S01。
- **解释边界：** 用户可以选择以新导入覆盖其看到的旧内容，但没有自然授权覆盖预览之后别人保存的新事实。单窗口顺序操作未必触发。
- **建议合同：** 替换命令携带用户确认时的旧记录或持久版本；前提改变时拒绝并要求重审差异。具体版本粒度待设计，不预设全库版本号。
- **后续验收：** 两份预览交错提交产生明确冲突；正常冲突选择、月结替换及同请求重试不退化；事实与修订审计一致。

### DB03 · P1：证券 ID 不变，市场、代码和币种却能改写

**证券名称可以更新，证券身份变化必须有单独规则。** 当前普通更新没有区分这两种行为；旧成交通过 JOIN 读取当前证券行，因此会被重新解释。

- **证据：** 已有 `HK:700 / HK / 700 / HKD` 成交；只更新同 ID 的证券为 `US / OTHER / USD`，不传新成交。旧成交读取出的证券身份随之改变，但执行表原币种仍为HKD。
- **定位：** `validateInstrument`、`putInstrument`、`getExecutions` 与 `mapExecutionRow`；详见 S02。
- **解释边界：** 正常解析器通常产生规范 ID，可降低误触概率；API/Store 的约束仍不足。真实代码更名等业务事件也不应与普通名称修改混为一谈。
- **建议合同：** 明确不可变身份字段、可更新展示字段及身份纠正命令；命令必须说明对旧成交与审计的影响。
- **后续验收：** 仅更新名称成功；相同 ID 改市场/代码/币种被阻断或按明确纠正流程处理；原始事实与读取解释一致。

### DB04 · P2：普通写入口未统一验证数字与时间的业务含义

**“字段是字符串”不足以保证它是合法成交。** 文本金额应继续保留精度，但所有正式入口需要一致的有效值规则。

- **证据：** 虚构普通成交带非法时间、非数字数量、负价格及坏费用字符串，经过真实 `mergeTradeData` 后原样落库。
- **定位：** `validateExecution` 只做部分形状检查；无法形成正常候选的输入被作为 unmatched 接受，之后写入。修订入口已有更严格 Decimal／时间校验；详见 S03。
- **解释边界：** 来源证据不足但数值合法的成交可以保留；这不同于语义非法。正常解析器的上游校验不能覆盖所有服务写入口。
- **建议合同：** 统一数量、价格、费用、时间及精度规则，同时保留仅日期、未知费用、结算原币和模拟运行的合法表示。
- **后续验收：** 非法值稳定拒绝且批次不半写；高精度数值原文往返不变；未知费用不补成已知零；合法日期精度与结算来源不丢失。

## 4. 首页未展示：目前模型审查指向什么

**本轮最直接的解释是“资格范围和提供者缺口”，不是已证实的数据库未连接。** 这与上述写入问题相关但不等同；没有证据证明四个写入反例就是当前首页为空的实际诱因。

### DB05 · P1：完整性缺口应说明影响哪项结论、哪个范围

**当前诊断进入全局未知后，无法充分表达“这条材料只影响账户B的港股”。** `financial-acquisition.ts:227–248` 汇总来源/历史缺口，`financial-source-model.ts:62–70,176–189` 对选集仍使用不接收选集的全局原因，`financial-view-model.ts:87–130` 因此拒绝总量或不构建序列。

静态反例是：A账户美股资料完整，B账户港股辅助持仓缺少对应成交，选择A/美股仍继承全局未知。**该反例本轮尚未执行。** 如果材料完全不能确定归属，扩大阻断可能合理；问题是当前结构不能清楚区分“完全无法界定”与“已经知道不属于本选集”。

建议将每条证据的归属、有效期间、支持/反驳的结论及缺口分别表达，再判断当前所求结论。月结单余额或零成交月份应能作为独立材料保留，不应为通过校验制造成交，也不应把所有诊断删除或一律改为完整。验证应覆盖跨账户/市场、零成交、未知归属和被新来源替代的旧证据，继续坚持未知不等于零。详见 QF01。

### DB06 · P1：历史供数缺口明确存在，但维持原暂停

**正式采集中的历史汇率观测与生命周期来源覆盖固定为空，历史域仍未接线。** `financial-acquisition.ts:171` 的两项空输入、workspace `:2286,2297,2304` 的 `not-wired`／抛错是当前代码事实。

这不表示所有本币期间指标都不能计算，也不表示本项目没有任何汇率存储。它说明“已有成交”尚不能自动满足“全历史和跨币种历史结论”。不能用第一笔成交推定开户起点，不能用当前汇率冒充历史汇率。

后续需要先决定覆盖证明的来源、起止时间及汇率时间规则，再接通领域输入。**本报告只记录阻塞，不恢复财务 P1/F07 或 Bars，也不重置原验收轮数。** 详见 QF02。

### DB07 · 验证缺口：≤1秒目标需要完整链路数据

**目前可确认采集成本随整个事实集合及多证券行情范围增长，不能在本轮定量归因超时。** 通用 bootstrap 读取全量事实与导入记录；首页对全部 summaries 读取各自所需日线后再选集。行情已经有按证券、日期范围读取，不能说成“无界读取全部行情”。交易库 collection-only 分支也已减少额外采集。

后续计时应覆盖SQL、序列化、传输、浏览器解析、领域计算、提交和绘制；沿用已确认的“本地数据齐备、完整首屏≤1秒”边界，覆盖浏览器冷/热访问、服务重启后首读、导入或修订后的首次打开。进程启动与外部补数另计。先实测再决定按范围规划输入、缓存或查询投影，不以提前显示部分列表代替完整首屏。详见 QF04。

## 6. 对候选方案的模块级意见

**候选方案把事实保存、证据判断和页面发布分开，方向与实际问题相符；下一步应先写清对象之间的约定。** 以下是建议职责，不是新增表或立即重构的实施决定。

|处理模块|需要持有或处理的数据对象|必须说清的约定|
|---|---|---|
|导入与事实保存|候选成交、稳定账户身份、证券身份、来源定位、提交前提、保存结果|不同账户不误合并；合法事实不因来源未知而丢弃；非法值不保存；迟到替换不静默覆盖|
|成交修订|旧事实、修订后事实、原因、范围与预期版本|何时允许改身份；事实与审计原子提交；幂等与冲突反馈|
|一致读取|所求范围、数据集合、本次读取凭证|内容/计数/摘要一致；凭证不冒充历史完整性或持久版本|
|来源与资格判断|独立证据、归属、有效期、影响范围、支持的结论、缺口原因|证据不强挂某笔成交；局部缺口只影响已知范围；真正未知仍保守处理|
|页面供数与发布|选集、指标输入、版本、可用性、原因与最终展示结果|列表、持仓、期间、历史分别有资格；整组一致；失败/空/未知/加载可区分|
|复盘与证据保留|草稿/正式版、版本号、原回合引用、冻结证据与查询投影|保留现有CAS；旧稿不因事实修订被删除；回合变化的关联政策另行决策|

主要数据对象不必各对应一张表或一个类。首先用输入、输出和不变量划清责任，避免由浏览器、Store、解析器各自实现一套不同的成交规则。

还有四项待定边界：同 execution.id 的核心字段变化是否必须冲突；unknown→live 是否可自动升级；旧复盘对修订后新回合如何关联；普通设置是否接受最后写入覆盖。它们的反例或业务规则尚未完成，不列为已经发生的损坏。详情见 S/R 系列与 QF03、QF05、QF06。

## 7. 建议的后续决策及验证顺序

**先批准规则，再实现最小闭环，最后证明性能。** 本轮不自动开启下面的开发；原暂停任务保持原状。

1. **事实边界审定。** 确认账户/证券/成交身份、合法数值与时间、替换前提。把DB01–04及合法边界样本固定为契约反例，决定是否需要额外数据库约束。
2. **证据与资格审定。** 用同账户不同市场、跨账户、零成交月份、未知归属四类材料解释DB05。决定影响范围与独立证据对象，再讨论表结构。
3. **保留与追查审定。** 明确修订后回合和正式复盘的关系；区分最新缓存与固定证据版本。不要自动改写旧正式稿。
4. **按授权恢复验证。** 若后续恢复相关任务，在隔离数据库验证导入→读取→页面→修订→返回→刷新，并以桌面批准设计进行独立视觉/功能验收；性能单独按≤1秒门槛测量。

审查材料与产品验收分开：本轮没有修复、迁移、重写数据、启动产品服务或发布。现状、三份独立意见、逐字段附录和证据共同组成此次交付，入口见[阅读导航](README.md)。
