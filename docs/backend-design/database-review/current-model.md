# 数据库建模现状：现在存了什么，页面如何使用

**当前数据库能够保存交易、导入来源、复盘和行情，但首页展示需要的“数据是否足够、属于哪个范围、能否计算”并不全部直接存于表中。** 因此，交易库有记录而首页为空，不能直接推断为数据库没连接；必须继续检查读取、资格判断和发布环节。

本篇只描述现状。建议与问题优先级见[综合审查意见](REVIEW.md)，逐字段结构见[数据库结构附录](schema-reference.md)，开源对照见[公开实践](external-practices.md)。

## 1. 本文依据及适用边界

**本次检查的是当前工作区代码定义的数据库，不是对在线交易数据的盘点。** 版本基点为 `58bf0d90e68ddc634de180b3f5c3d16a089f0eb3`，工作区含此前未提交修改；不能将本报告称为远端 master 的审查结论。

- 已核实：固定 Node 26.0.0／SQLite 3.53.0，在纯内存空库依次执行全部14次迁移，得到45张业务表及1张迁移记录表。
- 已核实：数据库结构、主要读写代码、页面供数路径，以及使用虚构记录调用真实存储代码的最小反例。
- 未核实：在线业务库应用到哪次迁移、实际记录数量和损坏情况、当前桌面页面是否修复、完整首屏是否达到1秒。

重建方法及源码指纹见[证据目录](../../../.scratch/database-model-review-2026-10-26/evidence/)。迁移脚本中的约束与实际业务数据的质量是两件事，本报告分别记录。

## 2. 先理解六个词

**审查的关键是区分“交易事实”“证明材料”和“计算结果”。** 它们相关，但不能互相代替。

|用语|普通读者可以这样理解|技术对应|
|---|---|---|
|证券身份|这一笔交易买卖的究竟是哪只证券；市场和代码共同参与区分|`instruments`、`instrument_id`|
|成交事实|账户在某时买卖多少、价格与费用是多少|`executions`|
|来源证据|记录来自哪份文件、哪一行；它能证明哪些事实|导入批次、成交来源、月结单证据等|
|交易回合|将一组成交按当前业务规则组织成一次持仓过程|由成交推导的 episode；不是一张成交明细表|
|完整性|在指定账户、市场和时间范围内，材料是否足够支持某个结论|枚举完整、期间覆盖、估值所需行情等不同判断|
|发布结果|页面最终允许展示的数值、列表或“暂不可用”原因|首页计算与展示模型；不是数据库读取成功的同义词|

专业附加词：**外键**保证一条记录引用的父记录存在；**事务**使一组操作同时成功或同时撤销；**版本冲突检查**要求保存前仍是用户读到的旧版本；**投影表**是为查询方便从主要业务记录生成的结构。后文的“原始文档”和“投影”主要用于复盘模块，不表示所有表都采用这套机制。

## 3. 从网页功能理解数据领域

**当前模型围绕成交复盘建立，财务辅助数据采用混合存储，首页主要读取已有事实再计算。** 以下是逻辑分组，方便理解；它不要求将每组立即拆成独立服务。

|领域及表数|保存的内容|支持的网页功能|需要特别区分|
|---|---|---|---|
|交易与导入：4张|证券、成交、导入批次、成交修订|导入预览与确认、交易库、纠错、筛选|来源文件相同不等于成交身份相同；账户不能在去重中丢失|
|行情：6张|日线、分时行情、覆盖区间、供应商代码、采集任务|图表、回放、估值及缺行情提示|有行情记录不等于整个持仓期间覆盖充分|
|复盘：28张|旧复盘和建议标签；新复盘文档及计划、评价、保留证据、冻结指标等查询结构|复盘编辑、正式完成版本、历史依据、回放后的评价|新复盘有文档主记录和派生表；不能简单按表数判断重复设计|
|设置和资金辅助：2张|设置 JSON、账户暂定本金|现金基准、参考资本、本金、汇率和显示设置|部分重要业务对象藏在通用设置内，并非均有独立业务表|
|维护与迁移：5张|旧数据迁入记录、TradingView账户迁移操作及依赖／别名／前后快照|迁移预览、提交、冲突检测及回滚|应用的数据迁移记录与数据库结构迁移记录用途不同|

另有 `schema_migrations` 记录数据库结构版本，不属于上述45张业务表。完整分组及每张表的字段、关系见[附录](schema-reference.md)。

### 3.1 交易与导入：证券是父对象，成交是核心事实

**证券身份集中保存，成交通过引用读取证券信息。** `executions.instrument_id` 引用 `instruments.id`；`batch_id` 可引用导入批次。删除证券时限制仍有关联成交的删除；删除导入批次会将成交的批次引用置空。

成交保存账户、方向、时间、数量、价格、费用，以及来源证据。数量、价格、费用使用文本保存；应用使用 Decimal 计算。这种形式保留十进制原文，但仍需业务校验，文本本身不会保证它是有效金额。

导入批次保存文件指纹、记录数量、对账与月结单证据；`trade_revisions` 保存有原因及前后记录的修订。**普通导入合并和审计修订是两套入口，当前保护力度不同**，详见综合报告的写入风险。

### 3.2 行情：行情值和“是否齐备”分开保存

**行情表保存观察值，覆盖表保存采集与缺口状态；二者都不是成交事实。** 日线按证券、日期、复权方式区分；其他行情还按周期与时间戳区分。供应商映射单独保存，避免证券内部身份直接依赖外部代码。

日线、分时行情带有供应商、来源代码、币种、采集时间等信息；分时表另有知悉时间字段。当前结构不代表保留了行情每次更正的所有历史版本。历史重算能否完全复现，需要结合保留版本、汇率和计算政策另行验证。

本轮只审查，不修改行情柱线（Bars）任务。

### 3.3 复盘：主要文档与查询结构在同一事务更新

**新复盘模块已经有较完整的“先校验版本，再保存，再生成查询结构”的设计。** `recall_documents` 保存草稿、最近正式版本和版本号；计划、评价、指标与关联表则支持结构化查询和保留历史依据。

保存时先取得写锁，再核对预期版本；版本不符则拒绝保存。正式完成是单独命令，自动保存草稿不会直接覆盖已有正式版本。各类投影在同一事务更新，因此不应把“文档＋关系表”本身视为缺陷。

旧复盘 `reviews` 仍然存在，页面还包含兼容及完成状态桥接。交易回合由成交推导，修订影响回合后如何对应已有复盘，是应继续保留的专项验证边界。

### 3.4 资金辅助：专用对象与通用设置并存

**当前不是完整券商现金账本，而是围绕既定页面需求保存参考基准和辅助数据。** 现金基准、参考资本、本金配置、汇率等由不同服务读写；多类对象保存在 `app_settings` 的不同键下。账户暂定本金另有专表，相关历史也使用设置保存。

现金基准存储类已有版本检查和历史保留，说明“存在 JSON”并不等于“没有业务规则”。但不同入口、不同键的并发保护和版本语义并不天然一致，需要逐条检查，不能由表级 `json_valid` 推断业务正确。

目前没有一个通用账户主表统一约束所有成交的账户身份。是否建立账户对象，应先明确账户别名、迁移、实盘／模拟范围及旧数据兼容，再决定是否增加表；不能直接将所有旧账户判为非法。

## 4. 一笔记录怎样走到首页

**首页和交易库可读取同一组成交，但它们并不采用完全相同的展示资格。** 数据链分为六步，每一步都可能成功、失败或证据不足。

```mermaid
flowchart LR
  A[导入文件与人工选择] --> B[解析与预览]
  B --> C[存储入口校验与去重]
  C --> D[SQLite 成交及来源]
  D --> E[读取与响应绑定校验]
  E --> F[账户市场筛选与完整性判断]
  F --> G[持仓财务计算及页面发布]
  E --> H[交易库列表与回合组织]
```

1. **导入并形成候选成交。** 解析器识别证券、账户及来源，预览处理重复和冲突。这里的正确解析不能代替服务器对写入请求的校验。
2. **保存事实和来源。** 存储入口执行事务、去重、证券更新和导入批次写入；修订有另一套前后记录检查。
3. **取得可核对的读取结果。** 首页专用读取在一个只读事务内收集数据，核对数量、孤立成交并生成内容摘要。它证明这次返回与所枚举内容绑定，不自动证明材料覆盖完整生命周期。
4. **形成页面候选集合。** 将成交组织为回合、按交易性质、市场、账户等形成可用集合。未明确性质和无法归属的证据需要独立规则。
5. **判断计算资格。** 生命周期、行情、现金或汇率等所需输入是否充分，取决于具体指标；读取成功不能代替该判断。
6. **发布页面结果。** 应区分“确实没有交易”“有交易但不能算”“采集失败”“仍在加载”。目前首页仍存在供数及范围判断缺口，见综合报告。

## 5. 数据库已经提供哪些保护

**现有设计有可保留的基础，不宜因为首页失败就整体推倒重建。** 连接开启外键、写入使用事务、迁移校验脚本摘要；复盘与部分资金对象已有版本检查。

|已有机制|能保证什么|不能由此保证什么|
|---|---|---|
|外键及删除规则|受约束引用的父记录存在|账户、派生回合及 JSON 内所有引用都正确|
|事务|同一操作中的多步修改共同提交或撤回|用户提交的预览没有过期；保存前后业务含义未变|
|迁移版本与摘要|已登记脚本与代码中的脚本一致|在线表和所有数据已通过业务质量检查|
|JSON语法约束及应用校验|部分内容格式有效、特定入口规则通过|所有入口采用同一规则；数字与时间都有效|
|主键、唯一约束与索引|既定键唯一，并支持对应查询|业务身份键足够完整；每条查询都快|
|首页读取摘要|响应内容与本次枚举凭证绑定|材料充分；历史数值可复现；首屏小于1秒|

连接与事务代码见 [sqlite.ts](../../../db/sqlite.ts:41)。本轮在空库发现的宽松类型、可空文本主键等只是数据库底线风险；可达写入缺陷另有真实存储反例支持，不能把两种证据混写。

## 6. 这份现状说明如何继续使用

**先审清事实身份、写入合同和展示资格，再决定是否调整表结构。** 新增表、改字段和搬迁计算都应服务于具体业务不变量，不以采用某种流行架构为目标。
