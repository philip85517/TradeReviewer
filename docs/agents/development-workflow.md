# 协调者 + Luna 分布式开发与预览交付

本工作方式由用户于 2026-09-12 指定，作为本项目后续开发的默认流程。用户当次明确指示优先；仅咨询或诊断不自动扩展为实施。

## 角色与任务边界

协调者负责理解需求、维护规格和验收标准、拆分工作、确定共享接口、处理集成问题、独立功能验收及最终聊天交付。默认主力实现交给明确指定 `gpt-5.6-luna` 的子代理；用户当次指定其他模型时遵从其选择，记录实际 model / reasoning effort，不仅在报告中使用模型昵称。模型选择不能替代以下验收门槛。

- 使用当前任务的子代理能力，不擅自创建用户侧独立任务。若指定模型或子代理能力不可用，明确报告限制，不假装已经委派，不静默更换模型。
- 独立工作按不重叠文件集合并行；共享文件指定单一负责人，共享接口先约定。需要顺序依赖的工作等待前置接口，不让两个实现者同时修改同一区域。
- 每份任务说明包含规格、需求和元素 ID、准确参考图、允许写入的文件范围、输入/输出接口、禁止项、测试与浏览器验收要求和报告路径。按[任务拆解标准](task-decomposition.md)派发；子代理不得自行再派代理或擅自扩大范围。
- UI 任务同时使用 [UI 任务与验收模板](ui-task-templates.md)，明确整页视觉负责人、跨组件数据/持久化闭环负责人和独立视觉审查者；组件票通过不能替代整页功能、端到端与视觉放行。
- 协调者在代理开发期间准备独立验收、检查运行环境或维护文档，不重复实现同一任务。
- 开始前检查分支、worktree、未提交修改和已有服务；保留其他工作，禁止为获得干净状态而重置仓库。没有用户要求，不推送、合并或发布远端。

## 设计契约与首次集成门槛

1. UI 实施前在功能任务目录建立 `DESIGN-COVERAGE.md`，逐项关联原始需求/规格锚点、元素 ID、准确画板或图片路径、阶段与状态、任务所有者、浏览器操作、预期结果及证据。采用[拆解标准的模板](task-decomposition.md)，所有范围内条目都有归属；不适用项写明依据，不能靠删行消除缺口。已确认设计的变更记录用户决策来源，不能在票摘要中静默省略。
2. 实现者先阅读关联图片、元素表和交互说明，再开始实现。当前仓库的项目约束和用户最新决定优先于交付包中归档的 workflow；归档副本只提供历史背景。设计与现有组件不一致时记录差异，按已确认目标实现；不能把旧组件的默认布局当成新的验收标准。
3. 先交付一条贯通必要界面、状态及持久化的最小用户旅程，涉及图表时使用真实图表。主图复盘的首条旅程至少为“遮住未来 → 下一根/播放/下一决策 → Text → 回看早期 → 保存/重开”。协调者完成真实图表验收和首张完整画面的视觉核对后，再扩大依赖其共享契约的侧栏、统计与导出实现。无此依赖的研究、数据准备和接口讨论可以并行。
4. 共享文件唯一负责人只解决写入冲突；协调者仍负责跨组件的顺序、默认状态、空间占用和任务可达性。每阶段明确侧栏内容顺序、首屏核心动作、默认折叠项，以及顶栏、底栏和阶段卡片的常驻高度预算。组件各自可渲染不能视为完整体验已经集成。

## 回放与三阶段状态契约

涉及回放、阶段切换或历史快照的任务，在并行实现前记录状态转移表：起始阶段、用户动作、行情可知截止、成交可知截止、目标阶段、可见/不可见字段、Text 归属、已看后续来源、视野策略及保存/重开行为。明确独立状态和必须原子更新的状态，至少覆盖以下适用边界：

- 区分逐根推进、播放/暂停、下一决策、恢复阶段、主动查看完整历史、重新开始回放。下一决策前进到约定目标，不得调用阶段恢复而跳到过去保存的更晚游标；同一根 K 的多次决策仍可分别访问。
- 首次买入前、未完成 K、缺失行情、最后一根/最后一笔分别定义可用动作。末尾或无数据时显示原因及下一步，不能保留看似可用但无效果的播放/快进按钮。已完成成果与可从头操作的回放入口必须可区分。
- 切周期、侧栏开合和刷新不隐式推进双游标；重开恢复所选状态。明确选取某次决策可以按契约跳到该决策边界，不能混同为布局操作或恢复别的阶段。
- 行情、轴范围、成交标记、回合状态、摘要、计划/评价和快照都受对应可知边界约束，不能从最终交易对象泄露买入事实、退出、已平仓或最终盈亏；未来高低点也不得影响早期定轴。阶段允许出现哪些字段必须逐项列明。
- 主动揭示结果、查看后续快照等入口统一记录已看后续的来源；返回早期、保存及重开不抹除来源。重新开始回放也不能把已经看过的结果伪装成首次盲看，早期补记需保留其真实来源。
- 回放推进必须让新增 K 线或目标成交出现在可见主图；刷新和侧栏 resize 按契约保留用户视野。不可用同一无差别恢复视野规则处理两类动作，验收须包含越过初始可见窗口的连续推进。
- 输入字段、图上 Text 编辑和中文 IME 期间阻止回放快捷键，编辑时暂停播放。未平仓样本的事后复盘区分可计算的已实现与浮动结果，不冒充最终平仓结果。

## 视觉验收贯穿实现

第一张完整阶段画面出现即比较；新增侧栏内容、三阶段区域或底栏入口后重新比较受影响画面，不等全部任务结束。设计与产品对照使用相同视口、阶段、导航展开状态、侧栏状态和近似文本密度。保存并排截图或叠图及实际尺寸测量，差异关联元素 ID，结论为满足、不满足或经用户批准变更。示例 K 线形状、证券名称和设计画板的说明区不作机械像素比对。

- 核对信息层级、控件顺序、默认字号/输入高度/命中区域、主图面积、顶栏底栏占高、价格轴与表单间距、Text 折叠及锚点、成交动作语义和首屏核心动作可达性。不能用“无重叠”“没有横向溢出”代替这些检查，也不能缩小所有文字来塞下内容。
- 三阶段区域必须验证默认展开/折叠、当前阶段识别、逐阶段回看、快照选择与主图的关系，以及正文长度增加后的占高；不能只检查渲染了三张卡片。下方摘要或表单不得无依据地挤占主图或把核心操作推到多屏滚动之后。
- 尺寸从本次批准的元素规格提取，不由各实现者独立设置。例如[主图复盘元素规范](../specs/2026-09-25-chart-first-review-ui-elements.md)要求字段输入 14px、桌面按钮至少 36px、触屏命中区至少 44px、侧栏 300–320px、轴与侧栏之间 14px 沟槽。约值记录实际值和视觉依据，不擅自发明宽松阈值。
- 主图复盘按 1440×900、1280×800、约 390px 窄屏及应用导航展开态验收，覆盖侧栏开合、长中文和长数值。断点根据工作区可用宽度和各区域实际占用推导，不直接复制 demo 视口断点。其他功能使用其批准规格中的视口。
- 真机软件键盘验收与桌面窄屏分开记录；没有真机证据时该要求仍为 `unverified`。没有对照截图和测量，不得写“视觉通过”。
- 浮动辅助动作同样纳入实际画面检查：核对其与价格标签、时间轴、绘图工具的相对位置，以及桌面和触屏命中尺寸。仅缩窄视口不能证明宽屏触控设备满足触屏尺寸。

## 提交远端与同步基线的默认流程

用户于 2026-09-20 确认：以后“提交修改至远端，并同步到基线”及等义指令，默认授权完整执行以下流程；基线固定为远端 `origin/master`，除非用户当次明确指定其他目标。

1. 检查当前分支、worktree、未提交内容及远端状态，仅提交本次任务相关修改，保留其他工作。使用对应开发分支；若当前在 master 或 detached HEAD，则为本次修改建立 `codex/` 开发分支。
2. 获取最新 `origin/master`，检查与开发分支的差异，解决必要的集成冲突并完成适用的测试、审查与验收。不得在必要检查失败时宣称可合并。
3. 先提交修改并推送开发分支到远端，设置其 upstream；不能以本地合并 master 后直接推送 master 代替此流程。
4. 使用该远端开发分支创建 PR，明确以远端 `master` 为 base。若同一 head/base 已有开放 PR，则更新并复用，避免重复创建。PR 描述写明问题、最终行为、验证结果与已知限制，并在当前任务附上 PR 链接。
5. 核对 PR 的最新提交、审查意见、合并冲突及必需检查，满足仓库合并条件后，通过 GitHub 合并 PR 至远端 master。上述完整指令本身已授权推送、创建和合并 PR，无需在每一步重复询问；不能绕过分支保护或失败检查。仓库未配置 CI 时应如实说明，并依据已完成的本地验证，不能虚称 CI 通过。
6. 合并后重新获取远端状态，确认 PR 为 MERGED 且合并结果位于远端 master；在保护现有修改的前提下，快进同步本地 master。若本地 master 已分叉、工作区修改阻碍更新或网络/权限受阻，保留现场并明确报告未完成的步骤，不使用强制推送或硬重置掩盖问题。
7. 最终回复提供 PR 链接、合并提交、远端与本地 master 的同步结果，以及仍未解决的限制。分支删除、其他 PR 的整合或仓库默认分支修改不属于此指令的自动附加动作。

仅要求“提交”或“推送某分支”时按该次明确范围执行，不自动扩大为合并 PR；用户当次明确指定的不同流程优先。本条是未来操作约定，修改此文档本身不等于立即执行一次远端提交与合并。

## 开发与审查

1. 明确本次验收项及数据边界，在本地任务目录记录状态。项目任务跟踪约定见 [issue-tracker.md](issue-tracker.md)。
2. 确认现有隔离 worktree 和相关测试基线，记录既有失败/警告。
3. 实现者先用可观察行为测试复现问题或描述缺失功能，再实现并执行相关回归；提交报告包含修改文件、失败到通过的证据、命令、结果和未决问题。纯文档修改按链接、内容一致性及差异审查验证，不为此运行产品全量测试。
4. 协调者检查实际变更，进行规格符合性和代码质量审查；必要时使用独立审查代理。不能把实现者自述等同于完成。
5. 把发现的问题交回文件负责人修复，再检查修复结果。共享接口调整必须同步到依赖任务并更新进度记录。

跨组件接口须验证实际消费者已接入。新增可选 callback、事件或状态属性时，派发说明同时写明提供方、调用方和最终可观察动作；单体调用 mock 成功不能证明页面接线。涉及图表 SDK 的异步绘制时，测试替身应保留关键的延迟提交语义，覆盖主动导航与 resize/阶段恢复同帧发生的次序；不能用同步 setter/getter 的 mock 排除真实库中的竞争。

保存异常验收须包含恢复后的真实字段：在隔离库验证一次保存失败及双窗口版本冲突，检查原输入保留、重试或显式重载后的字段/派生数值/保存状态一致，再次编辑保存不覆盖另一窗口的新字段。错误提示消失不能替代表单已恢复；行情刷新保留草稿的路径不能因显式重载修复而丢失本地输入。

图表的销毁同样属于生命周期验收：核对安装版本 SDK 的退订、primitive 卸载和 remove 调用顺序，验证已排队的尺寸/范围回调在销毁或回合切换后不再访问旧实例。测试应保留卸载可能触发重绘、remove 只能取消既有任务等真实行为；最终浏览器检查包括切换回合与 resize 后的新控制台错误，不能用吞异常或过滤日志代替修复。

## 数据安全与功能验收

- 真实交易数据库是受保护业务数据。凡会保存复盘、画图、修改设置、导入或删除的浏览器验收，使用 SQLite 一致性备份生成的独立数据库及独立端口。不能直接复制正在写入的单个 SQLite 文件而遗漏 WAL。
- 记录原始成交数量或内容摘要，并在验收后核对不变；日志和截图尽量不包含账户明细、完整账单或敏感配置。
- 会清空数据库或删除文件的自动化测试必须自行创建唯一临时目录，只清理自己创建的路径，并在结束时恢复原环境变量。不得把外部 `TRADEREVIEW_DB_PATH` 当作可删除的测试目标；显式隔离参数不替代测试自身的清理边界。
- 协调者亲自从浏览器完成核心用户路径，不能只依赖代理报告、单测或 HTTP 200。检查交互结果、浏览器错误和至少桌面/窄屏布局；具体宽度与边界按本次规格。
- 主图复盘从新回合完整操作：遮住未来 → 填写计划 → Text → 逐根/播放/下一决策 → 持仓修订且保留初始风险 → 逐次退出 → 主动查看结果 → 评价 → 返回早期 → 保存/重开 → 留存/导出。留存不作为继续揭示行情的门槛。另验证未平仓、无退出、无原计划、长文本、同 K 多决策/同日多退出等适用反例，不能只跳到预填好的组件状态检查控件存在。
- 每条路径记录点击序列、双游标前后值、应显示和应隐藏字段、真实图表时间轴/新 K 线/目标成交的可见性及截图。状态数值改变或传给图表的数组增长不等于播放成功，mock chart 测试不能替代真实绘图与视野验证。领域计算、自动化、浏览器行为和视觉符合性分别出结论。
- 金融指标检查口径、缺失值、费用、币种与实盘/模拟盘隔离；不能以零值替代未知数据。证券名称补全失败不得影响原交易身份。
- 集成后执行相关自动化、类型检查与构建，保留命令和结果。把未运行、失败或受外部服务限制的项目如实列出。
- 批量任务至少验证超过两批的真实调度、取消与有限重试，不能仅用分块函数单测推断整批完成。缓存更新验证连续两次成功刷新和旧版本读取；显示元数据变化不得污染交易修改的并发校验。
- 独立审查或网页验收发现的问题必须回到负责人修复，并更新报告中的完成声明；已有通过的测试数量不能覆盖未通过的反例。
- 原始账单规则更新须把成交财务字段与解析证据分开核验：先完整审计、再用生成时基线做只更新证据的副本预检；保留人工账户修正和申购补录。不同文档指纹不能仅凭金额相同自动替换；明确排除更新范围的文档仍须保留在原始审计中。
- 证据批量更新须在事务内核对生成计划所用的准确快照，并在提交前持久化可恢复的原始/目标证据。审计文件采用同目录原子替换，覆盖短写、Unicode、损坏回执与提交后中断恢复测试；重复执行不得新增成交或覆盖并发人工修改。
- 可选外部补全不能吞掉已成功的主结果。超时测试须覆盖整个入口的剩余时间预算，并验证底层请求确实取消；只测单个内部函数的等待时间不够。交易写入还须验证旧显示快照不会覆盖较新的元数据。
- “强制刷新”须检查应用缓存与浏览器 HTTP 缓存两层；服务重启不代表浏览器缓存清空。兼容性验收同时覆盖干净测试端口和用户已有预览 origin，避免旧缓存掩盖新字段。
- 批量后台请求须遵守现有 API 速率预算并为用户交互留余量；验证跨多批、取消后恢复和有限的限流重试。不能通过提高服务端限额、无限重试或要求反复刷新网页来掩盖调度问题。
- 并行开发结束后由协调者集中运行全量套件，避免多个全量运行争抢资源。发生超时时先保留原始失败，再单独复验或明确记录本次命令的超时参数，不通过隐藏失败或直接放宽项目默认配置制造通过结果。

## 验收状态与回归处理

- 任务的 `State` / `Status` 按[任务跟踪约定](issue-tracker.md)记录；实现报告完成只进入 `implementation-ready`，待集成为 `integration-pending`，已发现范围内缺陷为 `acceptance-failed`。协调者独立验证任务全部必需验收项后才能 `accepted` 并关闭该票。子任务接受不等于整个功能接受。
- 每个勾选项关联证据路径，包含代码版本/工作区状态、场景和验证结果；未完成的必需检查记 `unverified`。局部审查通过只能解除其已验证的局部问题，不自动覆盖浏览器、状态安全或视觉验收。范围内已知失败和必需未验证项都阻止功能完成；用户明确同意延期时记录范围变更依据。
