# 首页共用数据链路：预处理与更新机制分析

日期：2026-10-29。性质：基于现有证据的分析与后续实验建议，不是已批准的最终实现方案。实验分支：`codex/home-read-mvp-experiment-20261029`，产品基点 `0bbf7c4bfeabc325b4987966f93f45ff19f74d1f`。

## 一、结论

首页多个组件共用底层数据是合理的；问题是目前共用的是一份体积很大的原始来源包，打开页面时还要重复整理和校验。建议实验「提前生成可持久保存的页面数据、受影响时更新、页面读取摘要和分页」的组合。后台异步是可选的更新方式，不能用旧数字或后台排队掩盖“导入后首次打开 1 秒内展示最新完整首屏”的验收要求。

这里的“预处理数据”是根据原始成交、行情等生成的可重建结果，不能取代原始成交。持久化能让进程重启后继续读取；普通内存缓存则可以加速反复访问，但重启或失效后的首次读取仍需达标。

## 二、首页目前怎样共用数据

首页启动先读取 `/api/storage/bootstrap`；准备就绪后再并行读取 `/api/storage/homepage-source` 和汇率，接着读取证券行情并生成财务、持仓等页面数据。范围切换和期间变化具体路径不同，不能都理解为重新发起同一种请求。

| 展示内容 | 当前共享的数据和处理 | 针对该组件的独立耗时 |
| --- | --- | --- |
| 账户和市场筛选、标的搜索 | 从来源中的账户、成交和标的信息整理选项与目录 | 未单独测量 |
| 四项指标卡、表现曲线 | 同一个财务投影计算结果；期间变化使用已接受来源再次投影 | 未单独测量 |
| 持仓合计、持仓列表 | 来源、财务结果、行情和汇率共同生成持仓；目前本地排序、搜索和每页 8 行 | 未单独测量 |
| 历史财务 | 现有代码明确标示历史财务读取尚未接线 | 不能推算耗时 |

代码入口见 [trade-review-workspace.tsx](../../app/components/trade-review-workspace.tsx)（首次启动、首页读取、投影）、[home-surface.tsx](../../app/components/homepage-v25/home-surface.tsx)（持仓筛选与分页）与 [financial-view-model.ts](../../app/components/homepage-v25/financial-view-model.ts)。更详细的组件映射和测速边界见 [首页读取细分](homepage-read-breakdown-2026-10-29.md)。

目前后端内部虽然按 1000 笔分批处理，但随后把全部数据拼回同一响应；这与页面按 8 行分页并不等价。既有独立 HTTP 探针中，bootstrap 和首页来源各返回 34,315,599 字节；四次独立请求耗时约 4.106–12.404 秒，首次含开发编译。它们不是同一次浏览器导航的端到端链路，不能相加。桌面浏览器曾显示超时，尚无可靠的组件单独耗时和完整首屏毫秒值。

## 三、现有实验究竟证明了什么

真实历史数据的隔离实验包含 1,866 笔活动成交、236 个标的。7 次采样中位数如下：

| 实验方式 | 实际测量内容 | 中位时间 | 首次响应数据量 |
| --- | --- | ---: | ---: |
| A：现有完整来源 | 读取完整来源、编码解码和合同校验 | 8,474.79 毫秒 | 34,315,599 字节 |
| B：只缩小响应 | 仍读取和校验完整来源，再筛选分页 | 7,175.89 毫秒 | 3,250 字节 |
| C：预先准备精简事实 | 读取已准备事实及摘要，返回第一页 | 0.677 毫秒 | 3,250 字节 |

这些测量是进程内实验，没有 HTTP 和浏览器；A 返回完整包，B/C 返回精简结果，不能视为完整产品页面之间的直接性能对照。C 首次准备单次耗时 7,312.530 毫秒，其中仍包含完整来源处理与合同校验。C 不含完整财务、持仓金额、收益和图表，因此不能证明完整首页 1 秒达标。另一个更新实验以真实基数的非财务事实为初始数据，但之后的更新是合成的，尚待独立预审；一次增量更新约 2.3–3.1 毫秒，不能外推到真实财务更新或稳定性能。

## 四、可比较的路线

| 路线 | 怎样工作 | 判断 |
| --- | --- | --- |
| 继续优化现有完整链路 | 每次打开仍准备整个来源，尽量减少重复处理 | 可能改善，但未证明能满足 1 秒；数据包和重复计算依然是结构性问题 |
| 只改成摘要与分页接口 | 每次现算所有数据，只把需要的结果传给页面 | 能缩小传输，现有 B 仍约 7.18 秒，说明单靠缩小响应不足 |
| 准备可重建的持久化数据，并按变化更新 | 把重复计算前移；页面按筛选读取对应摘要、曲线和当前页 | 最值得进一步实验，但完整财务正确性、真实更新及 1 秒仍未证明 |

## 五、建议的职责划分

1. **原始数据层：**保存成交、账户、标的、已取得的行情和汇率等事实。原始成交仍是事实依据；缺失值不能被变成 0 或猜测补齐。
2. **预处理层：**按实际业务规则形成可复用的交易、持仓和必要的期间数据。按账户、市场、标的和时间组织只是候选，具体粒度须按财务规则验证。回补历史成交可能影响其后多个日期的持仓和收益，不能默认只重算当天。
3. **页面供数层：**按市场、账户、时间范围提供整体摘要、图表所需点、持仓合计和当前页。摘要覆盖整个筛选结果，而不是仅统计当前 8 行。首页和交易库应共享可复用事实，而不是互相照搬整个页面响应。
4. **更新与状态管理：**追踪成交、行情、汇率、规则和标的信息等来源的变化，标识结果对应的来源版本和计算时间；可显示“更新中”“更新失败”或数据缺失，避免把旧结果冒充最新结果。
5. **可选的热点缓存：**对常用范围的最终结果再做缓存；数据更新时明确失效，不能把缓存本身当成唯一数据依据。

查询范围、市场时区、币种/汇率、交易性质、行情和规则版本都会影响结果。不是所有金额或百分比都可以直接相加：例如组合收益率、跨币种金额和持仓成本要依据各自定义重新聚合。未知交易性质和缺少价格要维持真实状态，不能为了页面有数字而悄悄认定为实盘。

## 六、导入后如何更新：速度和正确性一起验收

例如导入 1 笔港股成交：系统先安全保存原始成交，再识别受影响的账户、标的和期间，重算相关持仓与摘要，发布同一版本的结果。若回补的是很久以前的成交，影响可能沿时间顺序传到之后的多笔交易及当前持仓。改名、汇率、行情或计算规则变化也要纳入更新触发条件。

可考虑在同一数据库事务中记录原始变化及待更新任务，后台处理时生成新版本，确认对应来源未变化后整体发布；中断后能发现待处理工作并恢复。建议将源变更与待更新任务放在同一数据库、同一事务内记录；新结果及其发布标记也须作为整体提交。SQLite 的 WAL 模式不保证跨多个数据库文件作为整体原子提交，若分库就必须另行设计恢复和版本检查（[SQLite 官方说明](https://www.sqlite.org/wal.html)）。实际事务边界、磁盘异常和恢复机制需要实验确认。页面读取同一发布版本的摘要和列表，避免新旧数字混搭。用户当前暂缓的是并发性能优化，这里的基本一致性是单机正常使用和故障恢复所需。

**关键约束：**既定目标包含导入或修订后的首次打开，且本地数据齐备时首页、交易库完整首屏都应在 1 秒内展示。如果后台尚未完成，显示“更新中”是诚实状态，但不能算完整首屏通过；显示旧结果也不能当最新结果通过。需要测量从真实导入/修订完成到最新结果准备好，以及首次打开到最新完整首屏的总耗时，按此前约定的起止点分别记录，不通过就继续优化或重新讨论体验，不能悄悄调整验收口径。

## 七、建议的下一组最小实验

仍在隔离工作树与数据库副本中进行，不修改共享业务数据库。财务 P1/F07、Bars、重复导入和并发性能任务保持原有暂停状态。

1. 先对首页各组件建立输入、共享计算和输出字段清单；分别标出财务、行情、汇率及当前未接线项，避免以非财务结果冒充完整页面。
2. 使用代表性数据，在实验环境构造摘要、曲线和分页结果的持久化原型，与原规则逐项对账；覆盖账户、市场、期间、空值、排序和翻页。涉及已暂停模块的真实开发或回归，先单独取得恢复授权。
3. 模拟并记录增量新增、历史回补、修订、行情/汇率变化、规则变化及进程重启；量化受影响范围和重建时长，核对持久结果与全量重算一致。模拟不等于真实导入验收。
4. 使用桌面真实浏览器测量完整链路：打开页面、服务准备就绪后首次读取、热访问、重启后首次读取，以及真实导入/修订后的首次完整首屏；分别记录各接口耗时、字节、后台准备、浏览器解析和展示，不把互相独立的阶段数字相加。
5. 当真实链路和每个场景都达标后，再决定最终的更新方式与产品改造；任何缺行情、数据更新中或失败的页面须保持诚实提示。

## 八、公开实践与参考

- [Apache Superset：仪表盘性能](https://superset.apache.org/admin-docs/configuration/dashboard-performance/)：建议对多个图表共用的昂贵聚合提前生成视图或定时更新的数据表，并结合缓存、按需加载；异步加载改善等待体验本身不等于完整首屏 1 秒达标。
- [Metabase：结果缓存](https://www.metabase.com/docs/latest/configuring-metabase/caching)：为仪表盘或查询保存结果，并可配置失效和提前刷新；文档也说明缓存失效后的首个访问可能需要等待重新查询。
- [Metabase：模型持久化](https://www.metabase.com/docs/latest/data-modeling/models/model-persistence)：将预计算模型结果保存到数据库，并配置更新；区分持久化模型与应用结果缓存。官方已建议使用 Transforms，该旧功能未来将弃用，且当前支持数据库不含 SQLite；这里仅借鉴思路，不是建议直接采用该功能。
- [Microsoft：物化视图模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view)：根据查询需要持久保存可重建的派生视图，并权衡更新与一致性。这里是通用设计模式，不意味着 SQLite 内置同名功能。
- [Microsoft：Cache-Aside 模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)：缓存缺失时仍需要访问源数据，缓存与源的更新也可能存在时间差；因此缓存本身不能证明首次访问或实时一致性达标。

这些是产品官方文档或通用架构指导，支持思路选择，不能替代本项目实际财务规则和端到端测试。
